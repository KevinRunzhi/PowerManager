# 1. 背景与问题

阶段 18 后，MVP-A 已具备活动记录、生活日结算、主观实际状态、备份恢复和能量球反馈。
本阶段不继续扩展视觉，而是处理代码审计中确认的四组工程风险。

1. App 冷启动时根组件和 `currentPreparationProvider` 会分别执行一次生活日准备；恢复前台时，
   根组件执行的准备结果没有进入 Riverpod 状态，页面可能继续显示恢复前缓存。
2. App 持续停留前台跨过本地 04:00 时没有刷新入口，旧生活日可能继续显示到下一次写入或重启。
3. 00:00～03:59 选择自定义完成时间时，UI 固定拼接“今天”的年月日。例如 02:00 选择
   23:00，本应解释为上一日 23:00，却会成为未来时间并被拒绝。
4. 活动删除立即生效且不能从 UI 撤销；“此刻校正”保存失败时没有任何提示；现有创建撤销
   使用独立定时器，连续 Snackbar 排队时窗口会从入队而非实际显示时开始计算。
5. JSON 导出并行读取七类表但不在同一只读事务中，写入并发时可能得到跨时刻快照；恢复前
   安全副本与数据库替换也不是同一个排他事务。
6. “分享 JSON”生成的临时文件在分享结束后没有清理，会在缓存目录持续累积。

这些问题不会改变算法公式，却会损害“当前生活日可信、误操作可恢复、备份可还原”的基础承诺。

# 2. 目标与非目标

## 2.1 目标

1. 冷启动只通过一个缓存的准备状态加载当前生活日；恢复前台后页面必定消费最新准备结果。
2. App 在前台跨过本地 04:00 后自动切换生活日、结算到期历史并刷新相关页面状态。
3. 自定义完成时间按“当前生活日”解释，覆盖凌晨、月末和年末边界，并继续拒绝未来时间。
4. 活动逻辑删除后提供 5 秒撤销，恢复必须走领域用例并完整重放派生结果。
5. 创建撤销和删除撤销共用同一反馈路径，连续反馈按实际展示顺序获得完整窗口。
6. “此刻校正”保存中、成功和失败均有可理解且可朗读的反馈，失败保留选择。
7. JSON 七类业务数据来自同一数据库事务快照；恢复前安全副本与替换对普通写入保持排他。
8. 分享生成的临时 JSON 在分享流程结束后尽力删除，清理失败不得伪装成导出失败。
9. 通过领域、应用、Widget、静态分析和 APK 构建回归证明上述行为。

## 2.2 非目标

- 不修改 04:00 边界、精力算法、恢复上限、规则版本或总结不可变规则；
- 不修改 Drift 表结构、数据库 schemaVersion、JSON schemaVersion 或七类导出字段；
- 不增加云同步、账号、后台任务、系统通知或新依赖；
- 不在阶段 19 实施阶段 17-B 的活动记录步数缩短；
- 不增加每日实际状态二次确认，不合并“每日实际状态”和“此刻校正”；
- 不做历史分页、结算增量扫描或 Shader 性能重构；这些需要真实性能证据后另立阶段；
- 不伪造七日真实使用结果。真实覆盖率继续作为发布后观察门槛。

# 3. 核心决策

## 3.1 当前生活日只有一个可观察准备状态

新增轻量刷新请求状态，至少包含：

- 单调递增的 `revision`；
- `PreparationTrigger`：`coldStart`、`resumed`、`lifeDayBoundary`。

`currentPreparationProvider` 监听该请求并执行准备。初始请求即 `coldStart`，根组件不得再额外
直接调用 `OperationPreparer.prepare`，从而消除双重冷启动。根组件监听同一 Provider 的错误，
不得启动第二条准备链。

恢复前台时递增请求并标记 `resumed`。所有依赖 `currentPreparationProvider` 的晨间状态、活动
预估、实际状态、昨日补充能力和历史回顾由 Riverpod 依赖关系自动失效；`appSettingsProvider`
也监听该请求，使跨生活日生效的待定基准线同步刷新。

## 3.2 前台 04:00 边界协调

`LifeDayCalculator` 提供“给定时刻之后的下一边界”纯函数。根组件仅在前台持有一次性 Timer：

1. 冷启动或恢复前台时根据注入的 `Clock` 计算下一本地 04:00；
2. Timer 到期后发出 `lifeDayBoundary` 请求并清除旧提醒展示；
3. 使用最新时钟重新安排下一边界；
4. 进入 inactive、paused、hidden 或 detached 时取消 Timer；
5. 返回 resumed 时立即刷新，因此后台错过边界也能补偿。

Timer 只负责触发刷新，不承载结算规则。结算、补应用待生效设置和当前投影仍由
`OperationPreparationService` 作为唯一事实来源。

## 3.3 自定义完成时间按生活日解析

新增无 Flutter 依赖的 `CompletionTimeResolver`。输入为当前时刻、小时和分钟，输出本地
`DateTime`，规则如下：

1. 构造“当前日”和“前一日”两个候选；
2. 仅保留与当前时刻属于同一 `LifeDay` 的候选；
3. 排除晚于当前时刻的候选；
4. 返回剩余候选中最新者；
5. 没有同生活日候选时报“已属于其他生活日”，只有未来候选时报“不能晚于现在”。

例：2026-08-14 02:00 选择 23:00，解析为 2026-08-13 23:00；选择 03:00 仍按未来
时间拒绝。2027-01-01 02:00 选择 23:00，解析为 2026-12-31 23:00。

Activity Sheet 的默认时间、预设时间、自定义时间和操作 ID 均使用注入的 `Clock`，避免测试
时 UI 时间与业务时间不一致。

## 3.4 删除恢复属于领域写入

`ActivityMutator` 新增 `restore(activityId)`，继续使用现有串行写入队列和数据库事务：

- 只恢复当前、未结算生活日的逻辑删除记录；
- 原 ID、`createdAt`、`completedAt`、分类、子类、时长、理论变化和规则版本保持不变；
- `status` 改为 active，`deletedAt` 清空，`updatedAt` 使用当前 UTC；
- 恢复后按既有顺序完整重放，重新持久化受恢复上限影响的 `appliedDelta`；
- 重复恢复 active 记录幂等返回；
- 不存在、跨生活日或已结算记录安全失败；
- UI 不得直接调用 Repository 或 DAO 绕过准备与结算检查。

## 3.5 统一撤销反馈时序

创建成功与删除成功调用同一 `_showActivityUndo`（或等价组件），差异仅为文案和反向用例：

| 原操作 | Snackbar | 点击撤销 |
|---|---|---|
| 创建活动 | `{子类} {时长} · 估计 {变化}` | `delete(id)` |
| 删除活动 | `已删除 {子类} {时长}` | `restore(id)` |

统一规则：

- 5 秒由 ScaffoldMessenger 中该 Snackbar 的真实展示生命周期负责；
- 不再创建平行的 5 秒 Timer，也不主动提前 `close()`；
- 连续操作使用 ScaffoldMessenger 队列，每条记录携带自己的 ID；
- 全局撤销窗口状态使用引用计数，不能由先结束的操作错误关闭后一个窗口；
- 仅明确点击“撤销”才执行反向写入，路由变化、超时或被移除均不自动恢复；
- 反向写入完成前保持提醒抑制；失败显示“暂时无法撤销，请重试”；
- 创建撤销窗口自然结束后，才允许计算低精力提醒。

## 3.6 此刻校正反馈

- 点击任一档立即保存，保留轻量流程；
- 保存中禁用三个档位、阻止关闭并显示小型进度；
- 成功 Snackbar 包含所选语义，例如 `已记录：比估计低`；
- 失败在 Sheet 内显示 `保存失败，请重试。`，保留 Sheet 与高亮选择；
- 错误使用 live region 语义，不输出异常、ID 或数据库信息。

## 3.7 一致导出、排他恢复与临时文件

`JsonExportService` 注入现有 `TransactionRunner`。应用版本可在事务外读取，七类业务数据和
设置必须在同一事务内顺序读取，再在事务外进行 JSON 编码。这样不会延长数据库事务到
Isolate 编码阶段。

恢复写入使用数据库外层事务包住以下步骤：

1. 从事务一致视图生成恢复前安全副本；
2. 将安全副本原子保存到应用支持目录；
3. 完整替换七类数据；
4. 任一数据库步骤失败则回滚替换，普通业务写入不能插入步骤 1 与步骤 3 之间。

分享临时文件由单独文件存储对象创建。分享 Future 结束后在 `finally` 中尽力删除；删除失败
只通过 Flutter 错误报告记录，不把已经完成的分享改报为失败。本机 latest 备份和恢复前安全
副本是持久文件，不参与该清理。

设置页把基准线保存、本机备份、临时导出和恢复视为互斥忙碌状态，避免同页并发写入。

# 4. 用户流程

## 4.1 跨生活日

1. 用户在 03:59 保持首页前台；
2. 到 04:00 后页面进入准备状态并得到新生活日投影；
3. 到期昨日被结算，待生效基准线按既有规则应用；
4. 首页晨间状态、活动、实际状态入口、历史和设置值同步切换；
5. 准备失败时首页显示既有重试状态，不继续伪装为旧生活日。

后台跨过 04:00 时，不要求后台 Timer 运行；返回前台后立即完成相同刷新。

## 4.2 凌晨记录

1. 用户在 02:00 打开活动记录；
2. 预设只展示仍属于当前生活日的时间；
3. 自定义选择 23:00，按钮显示并保存上一日 23:00；
4. 自定义选择 03:00，Sheet 内提示不能晚于现在；
5. 选择 04:00 之后且不属于当前生活日的时间，提示选择当前生活日。

## 4.3 删除与撤销

1. 点击删除后活动立即从有效列表移除，估计重新计算；
2. 显示 `已删除 {子类} {时长} · 撤销`；
3. 点击撤销后恢复原记录、触发轻触觉并刷新估计；
4. 超时则保持逻辑删除；
5. 撤销失败时不声称成功，提示用户重试或重新记录。

## 4.4 此刻校正

1. 点击档位后显示保存中状态；
2. 成功关闭 Sheet，并显示含所选档位的确认；
3. 失败时 Sheet 保持打开、原选择保持高亮，并提供重试入口。

# 9. 风险与回退

- 生命周期刷新会放大准备失败的可见性；正确行为是显示重试，不回退到可能错误的旧生活日。
- Drift 嵌套事务能力必须由恢复测试验证；若当前版本不支持，不得移除原子性要求，应拆出
  “已在事务内”的私有导出/替换路径。
- 分享插件返回时外部接收方应已取得文件句柄；若特定 Android 版本验证失败，调整为带短期
  租约的缓存清理，不得永久放弃清理。
- 统一撤销改动集中在 Home 与 ActivityUseCases，可通过回退 Stage19 提交恢复到 `ee9a908`；
  不需要数据库降级。
