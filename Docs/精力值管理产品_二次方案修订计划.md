# 精力值管理产品 二次方案修订计划

## 0. 文档目的

本文档用于组织 PowerManager 的第二轮方案修订。

本轮不以继续补充实现细节为起点，而是重新检查产品定义、数据证据链和 MVP 范围。所有重要产品取舍均采用“逐项讨论、用户确认、记录决策、再修改正式文档”的方式完成。

在对应决策确认前，不直接修改 PRD、规则配置、算法规则、Backlog 和技术方案中的正式口径。

---

# 1. 本轮修订目标

1. 明确精力数值究竟表示系统估计、用户预算还是用户自评。
2. 为个性化与基准线调整建立独立于系统计算结果的真实观测信号。
3. 把首版范围收缩为能够验证核心产品价值的 MVP。
4. 允许用户修正错误记录，避免错误数据进入趋势和个性化。
5. 降低规则迁移、周期状态机和跨日重算的首版复杂度。
6. 保留未来扩展个性化、趋势分析和跨平台能力的结构边界。
7. 修复上一轮文档修订后仍残留的交叉冲突。

---

# 2. 修订原则

- 先确认产品语义，再设计算法。
- 只有独立观测数据才能作为模型校准依据。
- 首版优先验证用户是否愿意持续记录和查看精力估计。
- 历史结果默认可追溯，不因普通操作静默变化。
- 用户误操作必须有可恢复路径。
- 每次只确认一个主要决策，避免多个取舍互相捆绑。
- 已确认决策先写入本计划的决策记录，再同步到正式文档。

---

# 3. 决策顺序

## DECISION-01：产品核心定义与数值含义

需要确认：

- 首页精力值是“系统估计值”“用户预算值”还是二者结合。
- 产品是否明确避免把数值表达为客观生理测量。
- “100”继续表示默认基准，还是仅作为界面尺度。

影响文档：PRD、规则配置、算法规则、新手引导、提示文案。

确认结果：

- 采用双轨模式。
- 首页主数值是系统根据早间状态、活动记录和当前有效规则计算出的“估计精力”。
- 用户提供的“实际状态”作为独立观测，不直接等同于系统估计值。
- 产品不得把估计精力描述为客观生理测量或科学能力评分。
- `100` 是默认尺度和初始参考点，不代表生理满值，也不是绝对上限。
- 后续个性化只能比较“系统估计”与“用户实际状态”，不得继续用系统计算结果自我校准。

## DECISION-02：真实状态观测方式

需要确认：

- 是否增加晚间或次日的实际剩余状态反馈。
- 是否允许用户随时对当前估计进行轻量校正。
- 反馈采用三档、五档还是数值滑杆。
- 哪些反馈可以进入个性化，哪些只用于展示。

影响文档：PRD、规则配置、算法规则、Backlog、数据模型。

已确认部分：

- 采用混合采集方式。
- 每个生活日提供一次轻量的实际状态确认；如果用户没有在当天完成，可在下一生活日首次打开时确认上一生活日状态。
- 用户可以在当天主动校正系统估计，不必等待每日确认。
- 每日确认和主动校正均允许跳过，不阻断活动记录和首页使用。
- 每日确认用于形成稳定的跨日观测；主动校正用于捕捉当天估计明显偏差。
- 每日实际状态采用五档绝对状态：`耗尽 / 偏低 / 尚可 / 良好 / 充足`。
- 主动校正采用三档相对反馈：`比估计低 / 差不多 / 比估计高`。
- 每日确认先收集用户实际状态，再展示系统估计和二者差异，减少锚定影响。
- 两类反馈必须保存原始选择和发生时间，不在采集层直接覆盖系统估计值。
- 两类反馈如何进入个性化推导，留到 DECISION-05 单独确认。

## DECISION-03：MVP-A 与 MVP-B 边界

需要确认：

- MVP-A 是否暂缓自动基准线调整和 personalFactor 学习。
- 首版周报是描述性总结还是包含调整建议。
- 高级规则编辑、历史规则迁移和复杂校准周期是否后移。
- 哪些功能是内部验证版必须具备的最小闭环。

影响文档：PRD MVP 范围、Backlog 优先级、技术里程碑。

已确认部分：

- MVP-A 不执行自动学习。
- MVP-A 使用固定且带版本号的默认活动规则生成系统估计。
- MVP-A 采集每日实际状态和用户主动校正，但只保存原始观测，不自动改变基准线或活动影响参数。
- MVP-A 的日结和周总结只做描述性反馈，不生成自动基准线调整建议。
- `personalFactor` 自动更新、自动基准线建议、复杂 CalibrationCycle 状态机进入 MVP-B。
- MVP-B 的启用条件应基于真实使用数据和观测完整度，而不是仅以开发完成为标准。
- MVP-A 必须交付：精简新手引导、早间确认、首页估计精力能量球、能量球手势与点击式备用入口、固定版本规则计算、当天记录与纠错、真实状态反馈、今日概览、低估计精力提醒、昨日描述性总结、滚动 7 个有效日总结、本地设置和 JSON 导出。
- MVP-A 明确延期：自动基准线调整、personalFactor 自动学习、7 日调整建议、复杂校准周期、高级规则编辑、历史规则迁移、复杂趋势图表、登录、云同步和自定义子类。
- MVP-A 的周总结采用滚动窗口，不建立用于自动决策的 CalibrationCycle。

## DECISION-04：活动记录与纠错

需要确认：

- 是否允许编辑和删除当天记录。
- 是否允许有限补记，以及补记窗口。
- 已结算历史是否只读。
- 活动分类是否增加“其他”。
- “睡觉 / 午休”是否改为“午睡 / 小睡”，夜间睡眠是否移入早间确认。

影响文档：PRD 活动记录、规则配置、Backlog、数据模型、重放规则。

已确认部分：

- MVP-A 允许在当前生活日内补记、编辑和删除活动记录。
- 补记时由用户选择大致完成时间，不要求精确还原开始时间。
- 当前生活日内的记录变化统一按稳定事件顺序重算当天系统估计和汇总。
- 04:00 生活日结算后，历史记录在 MVP-A 中只读。
- 不允许修改已结算历史，因此 MVP-A 不需要跨日编辑级联重算。
- 5 秒撤销继续作为快捷操作，但不是唯一纠错入口。

仍待确认：

- 无。

睡眠处理确认：

- 普通活动中的“睡觉 / 午休”改为“午睡 / 小睡”，继续使用普通短时档位。
- 夜间睡眠不作为普通活动记录，不要求用户填写 6～9 小时的精确睡眠时长。
- 次日早间确认增加“睡眠恢复感”，第一版采用轻量档位而不是精确睡眠测量。
- 睡眠恢复感作为早间上下文和后续分析观测；其是否直接参与估计公式在 DECISION-05 确认。

分类出口确认：

- 学习、实践 / 事务、休息恢复、娱乐消遣四个大类各增加一个“其他”子类。
- 四个“其他”分别使用所属大类的保守通用规则，不共用一个无法解释的全局默认值。
- MVP-A 不允许为“其他”自定义名称；自定义子类仍属于后续版本。
- 活动子类总数由 20 个调整为 24 个，规则表由 120 个单元格调整为 144 个单元格。

## DECISION-05：基准线与个性化算法

需要确认：

- 基准线是否先由用户控制，系统只提供建议。
- 自动建议依赖哪些独立观测数据。
- 是否取消使用系统计算的 finalEnergy 自我校准。
- personalFactor 的学习信号、启动条件和最小样本量。
- 透支是否继续直接降低次日初始值。

影响文档：规则配置、算法规则、校准测试。

已确认部分：

- MVP-A 保留“系统估计透支后，下一生活日自动下调 1～4 点”的原短期修正规则。
- 该修正被定义为产品中的短期负荷延续机制，不表述为对用户真实生理恢复的科学推断。
- 短期修正只读取紧邻的前一个生活日，空生活日中断，不跨日累计。
- MVP-A 中短期修正不得作为自动调整长期个人基准线的依据。
- 每日实际状态仍独立保存；系统估计透支与用户实际状态不互相覆盖。
- 当日初始估计中，只有早间综合状态直接产生数值微调。
- 综合状态继续采用 `差 -6 / 一般 0 / 好 +6`。
- 睡眠恢复感只作为解释上下文和后续分析观测，不在 MVP-A 中再次增减初始估计，避免与综合状态重复计分。
- MVP-A 的个人基准线默认值为 100。
- 用户可以在设置中手动调整个人基准线，允许范围为 60～140。
- 手动修改从决策所属生活日的下一个生活日起生效，不重算当前生活日和已结算历史。
- MVP-A 不根据记录或真实状态自动改变个人基准线。
- MVP-B 只有累计至少 14 个带每日实际状态观测的有效日后，才允许生成个人基准线建议。
- 基准线建议必须基于系统估计与用户实际状态之间的持续偏差，不再使用系统计算的 finalEnergy 自我校准。
- 只产生小幅建议，用户确认后从下一生活日起生效；不得静默调整。
- 只有活动记录、没有每日实际状态的日期，不计入基准线建议的最小观测门槛。
- MVP-B 的 personalFactor 只使用与具体活动记录绑定的直接反馈作为学习证据。
- 每日整体实际状态不分摊、不归因到当天某个活动子类。
- 同一子类积累足够的同方向直接反馈后，只生成小幅参数调整建议，并由用户确认。
- personalFactor 不静默更新，不因单次反馈变化，也不得让活动影响方向发生正负反转。

仍待确认：

- 无。

阈值策略确认：

- 当前不写死 MVP-B 的 personalFactor 样本阈值、建议步长和最终参数范围。
- 当前只确定以下不变量：必须有多条直接反馈、覆盖多个生活日、同方向占明显多数、单次建议保持小步、用户确认后生效、不得反转符号。
- MVP-A 内部测试数据应记录反馈数量、分布、跳过率和跨日覆盖，用于制定 MVP-B 的正式阈值。
- 未获得足够真实数据前，旧版 `3 条 / 2 日 / 70% / 0.05～0.15` 不再作为正式实现参数。

## DECISION-06：规则版本与历史数据

需要确认：

- 新规则是否只影响未来记录。
- 是否取消首版历史规则迁移。
- 历史页面展示当时结果，还是提供非破坏性的“按新规则模拟”。
- 记录编辑如何保留审计信息。

影响文档：算法规则、技术方案、数据模型、设置页。

已确认部分：

- MVP-A 的新默认规则版本只影响未来记录。
- 新规则从发布或选择发生时所属生活日的下一个生活日起生效。
- 当前未结算生活日继续使用当日已经确定的规则版本，不在日中切换。
- 已结算历史和当前生活日中的既有记录保留原 ruleVersion、theoreticalDelta 和展示结果。
- MVP-A 取消 ruleMigrationReplay，不提供最近 7 个有效日迁移重算。
- 每条活动记录仍保存 ruleVersion，保证历史结果可解释。
- 当前生活日内编辑采用就地更新，保留 `createdAt` 并刷新 `updatedAt`。
- 删除采用逻辑删除，写入 `deletedAt`；业务计算和默认查询只处理有效记录。
- MVP-A 不建立完整 ActivityRecordRevision 版本链，不保存每一次误输入的旧字段值。
- 编辑后的记录继续使用所属生活日的 ruleVersion 重新计算，不套用未来版本。

## DECISION-07：技术架构与数据模型

需要确认：

- Flutter、Riverpod、Drift 的保留范围。
- 是否减少首版代码生成和第三方依赖。
- DailyEnergyState 是派生状态、缓存还是结算快照。
- CalibrationCycle 和 PromptState 是否进入 MVP-A。
- 首版表结构、事务边界和测试分层。

影响文档：技术方案、Backlog、README、后续工程骨架。

已确认部分：

- MVP-A 使用 Flutter。
- 状态管理使用 Riverpod，但首版不启用 Riverpod code generation。
- 本地数据库使用 Drift / SQLite，保留类型安全、事务和迁移能力。
- MVP-A 暂不引入 Freezed。
- 路由优先使用 Flutter 原生方案，只有页面复杂度确实需要时再引入 go_router。
- JSON 导出使用 Dart 标准序列化或轻量手写映射；不为了少量模型强制建立完整代码生成体系。
- 当前生活日不持久化可变 DailyEnergyState；当前估计、档位和汇总由个人基准线、早间确认、短期修正及有效活动记录实时派生。
- 当前生活日发生补记、编辑或删除后，按稳定顺序重新派生，不执行跨日级联。
- 04:00 结算后创建不可变 DailySummary 快照。
- MVP-A 中已结算历史只读，因此历史页面直接读取 DailySummary，不反复重算。
- 结算操作必须幂等，同一 lifeDay 只能生成一个有效快照。
- MVP-A 使用以下最小数据集合：`app_settings`、`morning_check_ins`、`activity_records`、`energy_observations`、`daily_summaries`、`prompt_receipts`、`rule_config_versions`。
- `energy_observations` 通过类型区分每日五档绝对状态和随时三档相对校正。
- `prompt_receipts` 只保存展示、跳过和关闭等去重回执，不承担复杂跨周期状态机。
- MVP-A 不建立 `CalibrationCycle`、`SubcategoryPersonalFactor`、独立 `CalibrationFeedback` 和可变 `DailyEnergyState`。

## DECISION-08：交互验证与开工门槛

需要确认：

- 能量球手势原型的验收标准。
- 备用点击入口的地位。
- 首轮内部测试人数、持续天数和验证指标。
- 满足什么条件后再启用个性化与自动建议。

影响文档：PRD、Backlog、技术里程碑、验收矩阵。

已确认部分：

- MVP-A 先完成稳定、完整、可测试的点击式活动记录闭环。
- 能量球在手势未通过验证前承担估计精力展示和进入点击记录流程的作用。
- 连续滑动手势必须经过 Android 真机可用性测试，达到明确成功率和误触标准后，才升级为默认主入口。
- 手势未达标时不得阻塞 MVP-A 交付，也不得隐藏点击式入口。
- 手势与点击入口调用同一个活动记录用例和领域计算，不维护两套业务逻辑。
- 当前软件首先只供项目作者本人使用，不以多人公开测试为首轮目标。
- 第一轮内部验证由项目作者本人连续使用 7 个自然日。
- 开始 7 日验证前先完成开发冒烟测试，避免明显数据错误污染真实使用记录。
- 第一轮重点观察：每日是否愿意打开、活动记录是否顺手、分类是否覆盖、估计是否有参考价值、每日实际状态是否愿意填写、补记和纠错是否够用。
- 多人留存率、通用用户画像覆盖和规模化指标不作为 MVP-A 当前开工或验收门槛。
- 产品采用“个人优先、保留未来扩展”的定位。
- 默认活动、作息和交互优先满足项目作者本人的真实使用，但领域模型、规则版本和数据结构不绑定具体姓名、账号或单一设备。
- PRD 不再把多人大学生市场验证写成 MVP-A 当前目标；原大学生用户画像保留为未来可能扩展方向。
- 新手说明可以针对首次自用进行精简，但核心数值语义和操作说明仍需保留，作为长期维护文档和未来扩展基础。
- MVP-A 首轮由项目作者本人连续验证 7 个自然日，其中至少 5 天为主动使用日，不为了达标强行补数据。
- 7 天内至少完成 4 次每日实际状态确认。
- 活动补记、编辑、删除、重算和生活日结算不得出现数据错误。
- 复盘时需要确认估计精力对当天判断具有实际参考价值，而不只是视觉效果。
- 记录流程不得频繁出现无法归类或必须绕路的问题。
- 点击式记录入口必须稳定可用。
- 能量球手势只有在 Android 真机独立执行 20 次记录任务、至少成功 18 次且没有产生错误记录时，才升级为默认主入口。
- 7 日复盘通过后继续积累真实观测；达到至少 14 个带每日实际状态的有效日后，才允许讨论启用 MVP-B 基准线建议。

# 5. 验收方式

二次修订完成后执行：

1. 建立“产品规则 → 参数 → 用户故事 → 服务 → 数据表 → 测试”追踪矩阵。
2. 检查同一概念是否存在两个正式来源。
3. 检查每项自动调整是否有独立观测信号。
4. 检查所有用户输入错误是否存在恢复路径。
5. 检查 MVP-A 是否能够在不实现 MVP-B 的情况下独立运行。
6. 检查技术方案是否仍包含已延期功能造成的无效复杂度。
7. 将所有未决定事项明确标记为延期，不以模糊描述留在正式规范中。
