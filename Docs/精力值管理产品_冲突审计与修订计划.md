# 精力值管理产品 冲突审计与修订计划

> 2026-07-25 状态说明：本文记录的是第一轮冲突审计。二次方案已经改用《精力值管理产品 PRD v2（MVP-A）》及配套 v2 文档作为开发基线。第一轮中关于自动校准、personalFactor、CalibrationCycle 和 ruleMigrationReplay 的已修改结论仅供历史追溯，不再属于 MVP-A 实现范围。

## 二次方案新增的根因冲突

### CONFLICT-V2-P0-01：系统估计被当作真实结果自我校准

旧方案使用系统计算出的 `finalEnergy / initialEnergy` 再次调整产生该结果的 `baseEnergy`，缺少独立真实观测，并可能形成向上下边界漂移的正反馈。

二次方案决策：

- 明确区分系统“估计精力”和用户“实际状态”。
- MVP-A 不自动调整基准线或 personalFactor。
- 每日五档实际状态和随时三档校正独立保存。
- MVP-B 至少获得 14 个带实际状态的有效日后，才能依据估计与实际的持续偏差提出建议。

状态：已在 v2 正式文档中解决，待代码和 7 日自用验证。

### CONFLICT-V2-P0-02：首版复杂度超过核心价值验证需要

旧 MVP 同时包含规则迁移、跨日级联重算、校准周期和自动参数更新，但尚未验证单一用户是否愿意持续记录。

二次方案决策：

- MVP-A 只验证估计、活动记录、真实反馈和描述性复盘。
- 取消 MVP-A 的 CalibrationCycle、SubcategoryPersonalFactor、CalibrationFeedback 和 ruleMigrationReplay。
- 当前生活日实时派生，结算后保存不可变摘要。

状态：已在 v2 Backlog 和技术方案中解决，待实现验证。

### CONFLICT-V2-P0-03：错误记录缺少恢复路径

旧方案只有 5 秒撤销，之后不能编辑或补记，错误数据却会进入总结和学习。

二次方案决策：

- 当前生活日允许补记、编辑和逻辑删除。
- 5 秒撤销降级为快捷入口。
- 结算后的历史在 MVP-A 中只读。

状态：已在 v2 PRD、Backlog 和技术方案中解决，待实现验证。

### CONFLICT-V2-P1-01：夜间睡眠与最长 120 分钟档位不兼容

二次方案决策：

- 普通活动改为“午睡 / 小睡”。
- 夜间睡眠通过次日早间“睡眠恢复感”记录。
- 睡眠恢复感不与综合状态重复计分。

状态：已在 v2 规则配置中解决，待自用验证。

### CONFLICT-V2-P1-02：固定分类缺少未覆盖活动出口

二次方案决策：

- 四个大类分别增加“其他”子类。
- 使用所属大类的保守通用规则。
- 规则表扩展为 24 × 6。

状态：已在 v2 规则配置中解决，待自用验证。

## 0. 文档说明

本文档用于汇总 PowerManager 当前产品文档、算法规则、MVP Backlog 和技术方案之间仍存在的冲突、歧义与实现风险，并给出后续统一修订计划。

审计对象：

- 《精力值管理产品 PRD 定稿》
- 《精力值管理产品 MVP Backlog / 功能拆解》
- 《精力值算法规则初稿》
- 《精力值管理产品 技术方案初稿》
- 根目录中的 PRD 讨论稿，仅用于追溯未进入正式文档的历史决策

本文档不直接定义新的最终产品规则。文中的“建议方案”是后续修订的默认方向；涉及明显产品取舍的内容，需要确认后再同步到正式文档。

严重度定义：

- `P0`：可能导致数据错误、历史结果漂移或核心流程无法正确闭环，进入相关功能开发前必须解决。
- `P1`：规则无法唯一实现、体验行为不确定或数据模型不完整，应在对应开发阶段开始前解决。
- `P2`：不会立即破坏核心正确性，但会影响可理解性、可维护性、可测试性或后续扩展。

# 1. 总体结论

项目的产品方向、MVP 范围和总体技术架构已经比较完整，现有问题主要集中在以下五类：

1. **事件重放缺少规则版本边界**：普通重放可能重新套用当前规则，导致历史记录被静默改写。
2. **生活日状态准备不闭合**：App 持续前台跨过 04:00 时可能漏结算；空生活日的创建规则也互相冲突。
3. **算法仍有不可执行部分**：默认活动数值表、早间微调、周调整评分和抽样阈值尚未形成正式、唯一的规则源。
4. **个性化模型的符号假设不成立**：同一子类可能随时长在恢复和消耗之间切换，固定加法 offset 容易反转活动方向。
5. **校准周期和提示状态的数据模型不足**：无法完整表达周期、建议、延后、拒绝、重复启动和撤销后的状态变化。

因此，后续不建议立即大范围开发 UI。应先统一业务不变量、规则版本和校准周期，再进入领域层实现。

# 2. P0 冲突与修订建议

## CONFLICT-P0-01：普通事件重放可能改写历史理论值

涉及内容：

- 技术方案中 ReplayService 在每次重放时重新调用 `calculateTheoreticalDelta(...)`。
- ReplayService 同时用于新增、撤销、补做早间、修改基准线和规则变更。
- ActivityRecord 已持久化 `theoreticalDelta`，但没有规则版本或个人参数快照。

冲突：

普通新增或撤销记录本应只影响 `appliedDelta` 和当天汇总，但如果默认规则或 `personalOffset` 已变化，重放会用当前参数重算较早记录的 `theoreticalDelta`，造成历史结果静默漂移。

风险：

- 同一条历史记录在没有显式规则变更的情况下数值变化。
- 首页、昨日总结和趋势无法追溯当时使用的规则。
- 用户修改设置后，普通记录操作可能意外触发历史重算。

建议方案：

将重放拆为两种明确模式：

```text
operationalReplay
  使用记录中已保存的 theoreticalDelta
  只按事件顺序重新计算 appliedDelta 和每日汇总

ruleMigrationReplay
  使用指定的新规则版本重新计算 theoreticalDelta
  再重新计算 appliedDelta 和每日汇总
```

建议给 ActivityRecord 增加：

- `ruleVersion`
- `personalizationVersion` 或 `personalFactorSnapshot`
- 可选的 `lastRecalculationVersion`

需要修改：算法规则、Backlog US-5.3 / US-10.3、技术方案 ReplayService、数据模型和测试方案。

验收标准：

- 新增、撤销和补做早间不会改变既有记录的 `theoreticalDelta`。
- 只有显式规则迁移才允许改变 `theoreticalDelta`。
- 任意记录均可追溯计算时使用的规则版本。

---

## CONFLICT-P0-02：撤销语义仍混合了反向回滚与事件重放

涉及内容：

- PRD 使用“删除记录、回滚本次精力变化”的表述。
- Backlog 规定逻辑删除，但又要求“撤销回滚必须基于 appliedDelta”。
- 算法规则正确指出恢复上限具有顺序依赖，不能简单反向加减。

冲突：

如果撤销较早的消耗记录，后续恢复记录的 `appliedDelta` 也可能改变。仅反向应用被撤销记录的 `appliedDelta` 仍会得到错误结果。

建议方案：

统一规则为：

1. 将目标记录标记为 `cancelled`。
2. 作废关联反馈。
3. 使用 `operationalReplay` 重放该生活日全部 `active` 记录。
4. 禁止通过 `currentEnergy -= cancelledRecord.appliedDelta` 完成回滚。

需要修改：PRD 9.5、Backlog US-4.5、算法规则 5.3、技术方案 CancelActivityService。

验收标准：

- 撤销任意位置的消耗或恢复记录后，结果与从头播放剩余记录一致。
- 被恢复上限截断的后续记录会得到新的 `appliedDelta`。
- `cancelled` 记录不参与任何业务计算。

---

## CONFLICT-P0-03：App 持续前台跨过 04:00 时可能漏结算

涉及内容：

- Backlog 要求下一次启动或下一次记录前处理待结算生活日。
- 技术方案只在启动或回到前台时调用 SettlementService。
- ActivityRecordService 没有在写入前调用待结算处理。

典型场景：

```text
03:50 打开 App
04:00 App 仍在前台
04:10 创建记录
```

此时不会触发启动或前后台切换，旧生活日可能保持未结算状态。

建议方案：

所有业务写操作先调用统一状态准备入口：

```text
prepareForOperation(now)
  -> 计算当前生活日
  -> 按顺序结算更早的未结算生活日
  -> 准备目标生活日状态
  -> 返回可执行写操作的上下文
```

需要修改：Backlog US-5.4 / US-12.1、技术方案 AppStartupService / ActivityRecordService / MorningCheckInService。

验收标准：

- App 不切后台也能正确跨过 04:00。
- 跨日后的第一条记录写入前，旧生活日已经结算。
- 重复调用状态准备流程不会重复结算或重复创建状态。

---

## CONFLICT-P0-04：空生活日不建状态与启动时强制建状态冲突

涉及内容：

- SettlementService 和 Backlog 规定无记录、无早间确认的空生活日不生成 DailyEnergyState。
- AppStartupService 又要求确保当前生活日 DailyEnergyState 存在。

冲突：

用户只是打开 App 但没有任何操作时，技术方案会创建每日状态，而产品规则又把这一天定义为空生活日。

建议方案：

采用延迟创建：

- 启动时构造内存中的首页默认状态，不立即写 DailyEnergyState。
- 第一次完成早间确认或创建活动记录时，才创建 DailyEnergyState。
- SettlementService 只处理数据库中实际存在的生活日状态。

需要修改：Backlog US-5.4 / US-12.1、技术方案 AppStartupService、DailyEnergyState 创建规则。

验收标准：

- 只打开并关闭 App 不产生 DailyEnergyState。
- 空生活日不推进校准，不生成趋势点和昨日总结。
- 同一天首次写入时只创建一条 DailyEnergyState。

---

## CONFLICT-P0-05：产品大类不能直接决定精力变化正负

涉及内容：

- Backlog 使用“消耗类活动减少精力、恢复类活动增加精力”的描述。
- 历史讨论稿中，部分休息恢复活动在长时段会转为消耗，部分娱乐活动在短时段会恢复。
- 算法中的恢复上限实际上按 `theoreticalDelta > 0` 判断，而不是按活动大类判断。

冲突：

“休息恢复”和“娱乐消遣”是产品分类，不是数学符号分类。同一子类在不同时长下可能具有不同方向。

建议方案：

- 每个“子类 × 时长档位”独立定义正、零或负的默认值。
- 恢复上限只根据 `theoreticalDelta > 0` 应用。
- `totalConsumption` 定义为所有负 `appliedDelta` 的绝对值之和。
- `totalRecovery` 定义为所有正 `appliedDelta` 之和。
- 文档中不再把整个大类称为固定的“消耗类”或“恢复类”。

需要修改：PRD 精力计算描述、Backlog US-5.3、算法规则 3.3 / 5.2、技术方案 EnergyCalculator。

验收标准：

- 同一子类的不同时长可以分别产生恢复、无变化或消耗。
- 恢复上限的判断与活动大类无关。
- 总消耗和总恢复的统计口径唯一。

---

## CONFLICT-P0-06：personalOffset 的固定加法和方向规则不成立

涉及内容：

- 算法按“默认结果 + 子类 personalOffset”计算。
- 同一个 personalOffset 应用于该子类的全部时长档位。
- 算法用“消耗类 / 恢复类”决定 offset 更新方向。

冲突：

- 同一子类可能同时包含正、零、负的默认值，无法被固定归类为消耗或恢复。
- 固定 ±6 可能让较小默认值跨过 0，反转活动性质。
- 固定加法对短时活动的相对影响远大于长时活动。
- “估计偏重时向 0 调整”无法描述 offset 已经位于默认值另一侧的情况。

建议方案：

优先考虑将 offset 改为保持符号的强度倍率：

```text
personalFactor 范围建议为 0.7 到 1.3
adjustedMagnitude = round(abs(defaultDelta) * personalFactor)
theoreticalDelta = sign(defaultDelta) * adjustedMagnitude
```

默认值为 0 的规则单元格不参与自动强度学习。

如果保留加法 offset，则必须按每条记录的默认符号更新，并限制修正后不得跨过 0。

需要修改：算法规则第 3 章、技术方案 SubcategoryPersonalOffset、CalibrationService 和测试方案。

验收标准：

- 个性化不会把恢复自动改成消耗，也不会把消耗自动改成恢复。
- “偏轻 / 偏重”的更新方向对正值和负值都正确。
- 相同个人参数对不同时长档位的相对影响合理。

---

## CONFLICT-P0-07：校准周期缺少完整、幂等的持久化状态

涉及内容：

- UserEnergyModel 只有 `calibrationEffectiveDayCount` 和 `lastAdjustmentLifeDay`。
- 周调整需要支持建议生成、接受、拒绝、延后和再次提醒。
- 撤销活动、补做早间、规则重算都可能改变有效使用日或周期输入。

冲突：

现有字段无法唯一表达当前周期由哪 7 天构成、建议是否已经生成、用户如何处理，以及重复启动时是否应重新生成。

建议方案：

新增 `CalibrationCycle` 或 `AdjustmentProposal`：

| 字段 | 说明 |
|---|---|
| id / sequence | 周期唯一标识 |
| startedLifeDay | 周期开始生活日 |
| completedLifeDay | 第 7 个有效生活日 |
| effectiveDayIds | 本周期使用的数据快照 |
| status | `collecting / pending / accepted / rejected / deferred / invalidated` |
| baseEnergyBefore | 建议前基准线 |
| suggestedBaseEnergy | 建议值 |
| algorithmVersion | 生成建议时的算法版本 |
| decidedAt | 用户处理时间 |

有效使用日数量应优先从 DailyEnergyState 推导；如果缓存计数，必须定义幂等更新和回退规则。

需要修改：Backlog EPIC 9、技术方案 UserEnergyModel / CalibrationService / WeeklyAdjustmentService / PromptState。

验收标准：

- 同一个周期只生成一次建议。
- 重复启动不会重复推进计数或重复创建建议。
- 接受、拒绝和延后状态均可追溯。
- 周期完成后新增有效日归入下一周期，不改变已经冻结的建议输入。

# 3. P1 冲突与修订建议

## CONFLICT-P1-01：连续透支的 -5 下限不可达

透支分档最重为 `-4`，但连续透支章节又规定短期修正下限为 `-5`。如果每天只看前一天，`-5` 永远不会出现；如果允许连续累加，则缺少公式且与“每天仍按上表”冲突。

建议：第一版只依据紧邻的前一个生活日计算，删除不可达的 `-5` 描述；空生活日中断短期修正。若希望连续透支额外影响，应另行定义明确公式。

---

## CONFLICT-P1-02：早间三项输入中有两项没有明确用途

目前只有“综合状态”明确进入长期指标。自由时间和压力来源被保存，但没有说明是否影响早间微调、提醒建议、昨日标签或周调整。

建议：

- 综合状态用于早间微调。
- 自由时间仅作为上下文，不直接增加或减少精力。
- 压力来源可用于低精力时的大类建议或周期原因摘要。
- 如果后两项首版没有实际输出，应从早间强制输入中删除。

---

## CONFLICT-P1-03：核心规则仍未形成可执行的唯一来源

当前缺失：

- 20 个子类 × 6 个时长档位的正式数值表。
- 早间综合状态到微调值的映射。
- “高影响记录”的阈值。
- 同日两次抽样反馈的最小间隔。
- 周调整表现等级的确定性判定和唯一建议值。

历史讨论稿已有部分规则，但文件被 Git 忽略，不能作为正式实现来源。

建议新增正式文档《精力值规则配置 v1》，作为代码配置和单元测试的唯一来源。

---

## CONFLICT-P1-04：弱有效使用日的模型权重口径不一致

PRD 和 Backlog 说弱有效使用日在模型判断中“权重较低”；算法规则又把缺少早间确认的弱有效日列为异常日，不参与子类参数更新。

建议按用途分别定义：

- 校准进度权重：1，正常推进一个有效日。
- 基准线评估权重：给出具体数值，例如 0.5。
- 子类反馈更新：明确允许使用还是完全排除。
- 趋势展示：正常展示，但不参与某些模型指标时应有统一规则。

---

## CONFLICT-P1-05：个人基准线修改的生效时间不明确

PRD 表述为影响“之后”的初始精力，技术方案却把“修改个人基准线并影响当天”列为重放触发场景。

建议默认从决策发生时所属生活日的下一个生活日起生效，不重算当前生活日。若保留“立即应用到今天”，需要显式选择、二次说明和当天事件重放。

---

## CONFLICT-P1-06：最近 7 个有效日重算存在跨日级联

重算某一天可能改变 finalEnergy，继而改变下一天的 shortTermAdjustment、initialEnergy 和全部 appliedDelta。当前文档只描述逐日重放，没有定义传播边界。

建议明确：

- 从最早受影响生活日起按时间顺序重算。
- 定义短期修正是否传播到窗口后的第一个生活日。
- 已冻结的周期建议是否失效。
- 已展示的昨日标签和趋势如何更新。

---

## CONFLICT-P1-07：提醒状态存在两个来源

DailyEnergyState 中存在 `reminderFlags`，技术方案又建议独立 PromptState。两个来源会产生双写和状态漂移。

建议统一使用 PromptState，并设置业务唯一键：

```text
energy reminder: lifeDay + band
yesterday: targetLifeDay
weekly adjustment: calibrationCycleId
onboarding: global
```

---

## CONFLICT-P1-08：一次跨越多个精力档位时行为未定义

一条记录可能从高于 50% 直接进入透支。目前没有定义显示几个提醒、是否标记被跳过的中间档位，以及等于 50%、25%、0 时属于哪一档。

建议：

- 只展示变化后命中的最高严重度。
- 同时把已跨过的较轻档位标记为已处理。
- 明确阈值边界统一使用 `<` 或 `<=`。
- 精力提醒在 5 秒撤销窗口结束后展示；撤销后不得留下错误的已提醒状态。

---

## CONFLICT-P1-09：“昨日总结”可能实际来自多天前

Backlog 要展示最近一个有数据的已结算生活日。用户多日未使用时，这条内容可能并非昨天。

建议：

- 上一个自然生活日的数据称为“昨日总结”。
- 更早的数据称为“上次记录日总结”。
- PromptState 必须绑定实际被展示的目标生活日。

---

## CONFLICT-P1-10：事件排序缺少稳定的第二排序键

重放目前只按 `completedAt` 排序。两条记录时间相同时，恢复上限会使不同顺序产生不同结果。

建议统一为：

```text
ORDER BY completedAt, createdAt, id
```

并增加对应的确定性测试。

---

## CONFLICT-P1-11：今日概览的净影响排序可能隐藏高活动量

当前排序键是 `|sum(appliedDelta)|`。同一大类消耗 20、恢复 20 时净值为 0，会被排到最后，但该类实际产生了大量活动。

建议同时计算：

- `netDelta = sum(appliedDelta)`
- `grossDelta = sum(abs(appliedDelta))`
- `durationMinutes`

默认按 `grossDelta` 排序，展示 `netDelta`；或者在视觉上分别呈现消耗与恢复。

# 4. P2 改进项

## 4.1 数据约束

建议在技术方案中补充：

- MorningCheckIn：`UNIQUE(lifeDay)`。
- CalibrationFeedback：`UNIQUE(activityRecordId)`。
- PromptState：按业务作用域建立唯一键。
- DailyEnergyState：标准有效与弱有效状态互斥。
- ActivityRecord：限定时长档位、状态枚举、大类与子类组合。
- UserEnergyModel：固定单行约束。

## 4.2 时间和时区

建议：

- 时间戳统一以 UTC 保存。
- `lifeDay` 在记录创建时按本地时间计算后持久化。
- 用户之后切换时区时，不重新归属历史记录。
- 明确系统时钟回拨对 5 秒撤销窗口的处理方式。

## 4.3 动态学习关闭

需要明确关闭动态学习后：

- 已有个性化参数是冻结继续使用，还是恢复默认值。
- 是否继续显示抽样反馈。
- 重新开启后从旧周期继续，还是创建新周期。

建议默认冻结并继续使用已有参数，不再收集主动反馈；重新开启时创建新的校准周期。

## 4.4 数据导出

JSON 导出建议包含：

- `schemaVersion`
- `exportedAt`
- 规则版本
- 活动记录，包括 cancelled 状态
- 每日状态
- 用户模型和校准周期
- 设置和提示状态是否导出的明确边界

## 4.5 备用记录入口

备用点击式记录入口目前是 P1。建议提升为 P0，因为它同时承担：

- 新手兜底
- 无障碍操作入口
- 手势异常时的恢复路径
- 自动化 Widget 测试入口
- 能量球尚未完成时的领域联调入口

## 4.6 产品解释边界

最终剩余精力同时受用户能力和用户当天选择的活动量影响，不能直接视为能力测量。周调整文案建议使用“近期适用的估计基准”，避免表达为用户能力评分。

# 7. 推荐新增的测试场景

## 7.1 生活日与状态准备

- 03:59:59、04:00:00、04:00:01 的生活日归属。
- App 持续前台跨过 04:00 后创建记录。
- 多日未使用后按顺序结算。
- 重复调用 prepareForOperation 的幂等性。
- 只打开 App 不产生空 DailyEnergyState。

## 7.2 重放与撤销

- 撤销较早消耗记录导致后续恢复重新截断。
- 撤销恢复记录后重新计算当天状态。
- 普通重放不改变 theoreticalDelta。
- 规则迁移重放改变指定窗口的 theoreticalDelta。
- 相同 completedAt 时结果仍然确定。
- 事务中途失败后数据库无半更新状态。

## 7.3 校准与个性化

- 正值、负值和零值记录的反馈方向。
- 个性化后不发生符号反转。
- 第 7 个有效日只生成一个周期建议。
- 拒绝、接受、延后后的下一次启动。
- 撤销记录导致有效日失效时的周期处理。
- 动态学习关闭和重新开启。

## 7.4 提示与交互

- 一条记录连续跨过多个精力档位。
- 记录后 5 秒内撤销时不遗留提醒状态。
- 补做早间只撤回提示，不生成更重提示。
- 多日未使用时展示“上次记录日”而不是“昨日”。
- 能量球取消、回滑、超时和备用点击入口。
