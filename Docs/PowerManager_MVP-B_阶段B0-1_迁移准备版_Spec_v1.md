# PowerManager MVP-B 阶段 B0-1：迁移准备版 Spec v1

## 0. 文档状态

- 版本：1.0
- 日期：2026-08-15
- 状态：待实现
- 数据库版本：保持 schema v1
- 前置阶段：B0-0 文档与开工门禁
- 下一阶段：B0-2 schema v2 与备份兼容

## 1. 阶段目标

在第一次数据库结构升级前，证明手机中的 schema v1 真实数据拥有可识别、可解析、可恢复的
本机副本，并让用户能直接判断“是否具备升级条件”。

本阶段复用 Stage 14、16、19 已有备份能力，补齐升级预检和可审计状态，不重新设计备份格式，
不修改业务表，不运行学习器。

## 2. 用户结果

设置页的数据区域提供一个明确的“MVP-B 升级准备”状态：

- 未检查：说明需要先保存并验证本机备份；
- 检查中：禁止重复执行；
- 已准备：展示验证时间、备份时间、文件大小、schemaVersion 和完整性结果；
- 未准备：展示安全、可行动的失败类别；
- 数据在上次验证后发生变化：状态退回“需要重新验证”。

用户可以一键执行：

1. 统一生活日准备；
2. 生成事务一致的 schema v1 JSON；
3. 严格解析并验证内存结果；
4. 原子写入 latest 本机备份；
5. 从磁盘重新读取并再次严格解析；
6. 将备份指纹与当前一致快照指纹比较；
7. 保存升级准备证明并刷新设置页。

## 3. 范围

### 3.1 必须实现

- UpgradeReadinessReport 类型；
- MvpBUpgradeReadinessService 串行编排；
- 对 latest 备份执行磁盘回读验证；
- 当前数据与备份的稳定内容摘要比较；
- 记录最近成功验证的 UTC 时间、备份元数据和 schemaVersion；
- 设置页只读状态卡与“一键准备”动作；
- Data Health 复用同一报告，不复制判断逻辑；
- 备份或数据库变化后正确失效旧准备状态；
- 安全错误分类和重试。

### 3.2 明确不实现

- 不改变 AppDatabase.schemaVersion；
- 不增加、删除或重建任何 Drift 表；
- 不新增 observation contract 字段；
- 不创建 activity_feedback；
- 不运行影子或生产学习；
- 不自动恢复数据库；
- 不把用户真实 JSON、摘要或活动正文写入日志或 Git。

## 4. 数据合同

升级准备证明至少包含：

| 字段 | 语义 |
|---|---|
| verifiedAt | 完成磁盘回读与当前快照对比的 UTC 时间 |
| backupModifiedAt | latest 文件修改时间 |
| backupByteLength | 文件字节数 |
| backupSchemaVersion | 必须为 1 |
| backupContentDigest | 对规范化备份业务内容计算的摘要 |
| currentContentDigest | 同一算法对验证事务快照计算的摘要 |
| integrityStatus | passed 或 failed |
| failureReason | 安全枚举，不保存异常正文 |

摘要只用于判断备份是否对应验证时的数据，不作为安全加密。摘要输入必须排除导出时间、
App 版本和文件路径，否则同一业务数据重新导出会被误判不同。

准备状态不属于业务真源。若状态文件丢失，App 只要求重新验证，绝不影响数据库和已有备份。

## 5. 失效规则

以下任一事件发生后，先前“已准备”不得继续显示为当前有效：

- 任一七类 schema v1 业务数据发生写入；
- app_settings 发生业务值变化；
- JSON 恢复成功；
- latest 备份被覆盖、删除或元数据不匹配；
- App 检测到备份无法重新解析；
- 当前内容摘要与证明不一致。

可以采用“每次进入页面重新计算摘要”或“业务写入 revision + 打开页面复核”的实现。无论选择
哪一种，不能依赖容易漏写的 Widget 本地布尔值。

## 6. 实现步骤

1. 复核 Stage 16 的 LocalBackupService、LocalBackupStore 和 JsonBackupCodec；
2. 增加不包含易变导出元数据的规范内容摘要；
3. 新增 readiness store，采用临时文件加原子替换保存非敏感证明；
4. 新增服务，把 prepare、导出、保存、回读、摘要比较置于现有串行操作边界；
5. 失败时清理临时文件，保留上一份有效 latest 备份；
6. 设置页显示状态、动作和安全错误；
7. Data Health 读取相同状态；
8. 添加领域、文件、应用和 Widget 测试；
9. 完成模拟器演练；
10. 完成连接真机的一次备份、分享或导出、预览与恢复演练，并单独记录结果。

## 7. 自动化测试矩阵

### 7.1 摘要与服务

- 相同业务数据、不同 exportedAt 得到相同内容摘要；
- 任一业务字段变化使摘要变化；
- 列表输入顺序不同但语义相同得到相同摘要；
- 生成、内存校验、原子保存、磁盘回读和比对全部成功；
- 导出失败、写入失败、回读失败、解析失败、摘要不一致分别返回稳定 reason code；
- 任一步失败不删除原数据库，不覆盖上一份有效备份；
- 并发点击合并为一条串行操作；
- 恢复成功后旧证明失效。

### 7.2 Widget

- 未检查、检查中、已准备、数据已变化和失败状态文案；
- 处理中按钮禁用且无重复 SnackBar；
- 错误不泄漏路径、记录 ID、活动正文或异常堆栈；
- 200% 字号、小屏和横屏可滚动且无溢出；
- 返回页面后从持久状态重新判定，不依赖旧 Widget 状态。

### 7.3 回归

在 app 目录执行：

    dart format --output=none --set-exit-if-changed lib test
    flutter analyze
    flutter test
    flutter build apk --debug

在仓库根执行 git diff --check。

## 8. 模拟器与真机验收

### 8.1 模拟器

1. 有数据时执行一键准备，显示已准备；
2. 重启 App 后状态仍可验证；
3. 新增一条活动后状态变为需要重新验证；
4. 再次准备后恢复已准备；
5. 分享 latest 文件并取消系统分享，状态不受影响；
6. 使用有效备份完成预览、确认、恢复，再次验证聚合和摘要一致；
7. 损坏一份测试文件时只拒绝该文件，不改变数据库。

### 8.2 真机

1. 先记录当前聚合数量，不展示私人明细；
2. 保存并验证 latest 备份；
3. 将文件导出到用户可访问位置；
4. 在确认安全副本存在后完成一次恢复演练；
5. 对比恢复前后七类计数、生活日范围和完整性；
6. 重启 App，再次检查当前日和历史页；
7. 将结果写入独立验收记录，真实备份文件不进 Git。

## 9. 停止与回退

出现下列任一情况立即停止，不进入 B0-2：

- latest 备份不能稳定回读；
- 恢复后七类数据或设置不一致；
- 备份操作可能覆盖原数据库；
- readiness 显示已准备但当前摘要不匹配；
- 发现外键、摘要、活动重放或日总结异常；
- 真机备份没有用户可控制的副本。

本阶段没有 schema 变化，代码回退后数据库仍为 v1。readiness 证明可以安全丢弃并重新生成，
但 latest 和 before-last-restore 备份不得被清理。
