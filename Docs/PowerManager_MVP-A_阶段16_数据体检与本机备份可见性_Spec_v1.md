# 1. 背景与问题

当前设置页可以分享 JSON、恢复 JSON，并保存恢复前安全副本，但仍有两个使用摩擦：

1. Android 厂商分享面板不保证出现明确的“保存到本机”入口；
2. 用户无法在 App 内快速确认有效日、每日实际状态覆盖率和数据一致性是否足以继续验证。

阶段 16 增加一个固定的本机备份槽，以及只读数据体检页。它不新增埋点，也不改变业务
数据，只基于现有七张表、schema v1 校验器和本地文件元数据生成聚合结果。

---

# 2. 目标与非目标

## 2.1 目标

1. 设置页将“保存本机备份”和“分享 JSON”拆成两个明确动作；
2. 本机备份写入应用支持目录，采用临时文件 + 原子重命名；
3. 保存前后均使用 schema v1 严格校验，不能留下无法恢复的“成功备份”；
4. 显示最近本机备份时间、文件大小，并允许分享该文件；
5. 新增只读“数据体检”页，显示有效日、实际状态覆盖、记录计数和一致性状态；
6. 数据体检不复制活动明细，不输出 ID 或原始 JSON；
7. 体检结果明确说明 MVP-B 的 14 日门槛，但不得自动启用个性化。

## 2.2 非目标

- 不增加云备份、账号、跨设备同步或定时后台任务；
- 不保留无限历史备份，只保留最近一次用户主动保存的本机备份；
- 不把本机备份与“恢复前安全副本”混为同一个文件；
- 不自动修复异常数据；
- 不新增业务数据表或埋点表；
- 不实现 MVP-B 基准线建议、personalFactor 或规则自动调整；
- 不读取或展示私人活动明细。

# 3. 本机备份设计

## 3.1 文件位置与命名

应用支持目录中固定保存：

`powermanager-latest-backup.json`

恢复前安全副本继续使用：

`powermanager-before-last-restore.json`

两个文件目的、入口和生命周期独立。用户再次主动保存时覆盖 latest 文件；恢复操作只覆盖
before-last-restore 文件。

## 3.2 保存流程

1. 使用 `JsonExportService` 生成当前 schema v1 JSON；
2. 在内存中调用 `JsonBackupCodec.inspect` 严格校验；
3. 写入同目录临时文件并 `flush`；
4. 用重命名替换固定目标文件；
5. 重新读取目标文件并再次严格校验；
6. 返回文件路径、保存时间、字节数和导出文件名。

任何步骤失败：

- 不显示成功提示；
- 临时文件必须清理；
- 已存在的上一份有效 latest 备份必须尽可能保留；
- 不修改数据库。

## 3.3 设置页动作

数据区域调整为：

1. `保存本机备份`：主动作，成功后显示时间与大小；
2. `分享 JSON`：即时生成一份带时间戳的分享文件；
3. 存在 latest 时显示 `分享最近本机备份`；
4. `数据体检`；
5. `从 JSON 备份恢复`；
6. 存在恢复前安全副本时显示原有分享入口。

保存、分享、恢复互斥，处理中按钮禁用并显示明确状态。用户取消系统分享不算失败。

# 4. 数据体检口径

## 4.1 聚合指标

页面展示：

- 已结算生活日数；
- 有效生活日数，其中标准有效日与弱有效日分别计数；
- 带每日实际状态的有效日数；
- 实际状态覆盖率：`带实际状态的有效日 / 有效日`；
- 距 MVP-B 14 日门槛还差多少日；
- 晨间确认数；
- 活动记录数，另列逻辑删除数；
- 每日实际状态数；
- 随时校正数；
- 最近本机备份状态、时间与大小；
- schema v1 完整一致性检查结果。

有效日口径必须直接读取不可变日总结中的 `isStandardEffectiveDay / isWeakEffectiveDay`。
每日实际状态只计算 `dailyAbsolute`，随时校正不得混入覆盖率。

## 4.2 一致性检查

体检使用当前导出服务生成内存快照，并交给阶段 14 的严格校验器。通过时显示：

`完整性检查通过 · 0 项异常`

失败时只显示：

`发现至少 1 项一致性问题，请先导出备份并保留当前数据。`

不得在 UI 或日志中展示原始 JSON、活动名称、记录 ID 或底层 SQL。

## 4.3 MVP-B 门槛表达

- 0～13 日：显示当前进度与“还需 N 个带实际状态的有效日”；
- ≥14 日：显示“样本数量达到讨论门槛”，而不是“已启用个性化”；
- 始终附注：还需持续、可解释的估计偏差，并由用户确认后才能应用建议。

# 5. 数据体检页面

路径：`设置 → 数据 → 数据体检`

页面层级：

1. 顶部结论卡：一致性状态；
2. “验证进度”卡：有效日、实际状态覆盖率、14 日进度；
3. “数据概览”卡：六项聚合计数；
4. “本机备份”卡：最近保存时间、大小、分享入口；
5. 底部说明：结果仅用于自用验证，不代表医学判断或自动学习结论。

交互要求：

- 页面只读；
- 下拉刷新或显式“重新检查”触发新快照；
- 检查中显示稳定占位，不闪烁旧值；
- 失败显示原因类别和“重新检查”，不显示内部异常；
- 200% 字号、小屏和横屏可以纵向滚动，无横向溢出；
- 使用文字、图标和数值共同表达状态，不依赖颜色。

# 6. 技术设计

## 6.1 文件层

新增：

- `LocalBackupStore`：latest 文件的原子保存、读取路径与元数据；
- `LocalBackupService`：导出、保存前校验、写后校验编排；
- `LocalBackupMetadata`：路径、更新时间和字节数。

文件层不得引用 Widget 或直接弹出分享面板。

## 6.2 体检服务

新增 `DataHealthService`：

1. 并行读取总结、观测和导出快照；
2. 计算聚合计数与覆盖率；
3. 调用严格校验器检查快照；
4. 读取 latest 备份元数据；
5. 返回不可变 `DataHealthReport`。

Widget 只负责展示，不自行遍历业务实体或重新实现口径。

## 6.3 Provider 刷新

- 新增 `localBackupMetadataProvider`；
- 新增 `dataHealthReportProvider`；
- 本机备份成功后刷新二者；
- JSON 恢复成功后刷新体检报告与 latest 元数据；
- 页面重试只刷新体检 Provider，不修改数据。

# 7. 测试要求

## 7.1 文件与服务测试

至少覆盖：

1. latest 备份首次保存；
2. 第二次保存原子覆盖；
3. 临时写入失败保留旧备份；
4. 临时文件最终清理；
5. 写前校验失败不写文件；
6. 写后校验失败不报告成功；
7. 元数据时间和字节数正确。

## 7.2 体检口径测试

至少覆盖：

1. 标准、弱和非有效日正确计数；
2. 只有有效日上的 `dailyAbsolute` 进入覆盖率；
3. 随时校正与每日实际状态分开；
4. 0 个有效日时覆盖率安全显示；
5. 13、14、超过 14 日三种门槛文案；
6. 一致性通过与失败的安全表达；
7. 不读取活动明细用于页面文案。

## 7.3 Widget 测试

至少覆盖：

1. 设置页三个备份动作和体检入口层级明确；
2. 保存成功刷新最近备份信息；
3. 体检页展示覆盖率与门槛差值；
4. 检查失败不泄漏内部异常；
5. 重新检查可恢复；
6. 200% 字号、小屏无溢出。

# 8. Pixel_7 模拟器验收

1. 设置页点击“保存本机备份”，出现成功提示和最近时间；
2. 关闭并重启 App，最近备份状态仍存在；
3. “分享最近本机备份”能调起 Android 分享面板，取消后 App 正常；
4. “分享 JSON”仍能调起分享面板；
5. 数据体检页展示恢复进模拟器的真实聚合数据；
6. 覆盖率与阶段 12 审计数据或当前模拟器数据库一致；
7. 点击重新检查结果稳定；
8. 返回设置页路径正确，不改变数据；
9. 日志无 Flutter 异常、Crash 或 ANR。

---

# 9. 验收标准

1. 主动本机备份与恢复前安全副本是两个独立文件；
2. latest 保存采用原子替换，失败不会产生半份成功备份；
3. 保存前后均经过 schema v1 严格校验；
4. 设置页能显示并分享最近本机备份；
5. 体检所有统计口径与正式 PRD、算法规则一致；
6. 一致性检查复用阶段 14 校验器；
7. 页面不包含活动明细、ID、原始 JSON 或 SQL；
8. 14 日只表达讨论门槛，不启用 MVP-B；
9. 体检和保存操作不修改七张业务表；
10. 200% 字号与小屏无溢出；
11. `dart format`、`flutter analyze`、完整 `flutter test` 通过；
12. Pixel_7 模拟器流程通过；
13. 真机综合验收继续延期到 MVP-B 完成后。
