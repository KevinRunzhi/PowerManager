# 1. 技术目标

第一版技术目标：

- 离线可用，不依赖账号、云同步和服务端
- 精力计算结果稳定、可追溯、可重算
- 活动记录、撤销、生活日结算、校准等核心流程可单元测试
- UI 层尽量只负责展示和交互，不直接承载业务规则
- 本地数据结构支持后续版本扩展，如单条记录详情、云同步、更多趋势分析

第一版不追求：
- 服务端架构
- 多端同步
- 复杂机器学习
- 实时后台任务
- 高度复杂的图表能力

# 2. 推荐技术栈

## 2.1 客户端框架

推荐使用：

- Flutter
- Dart
- Material 3 或自定义轻量设计系统

理由：
- 适合移动端单体应用
- 手势、自定义绘制、动画能力较强，适合能量球交互
- 本地数据库、状态管理、测试工具链成熟
- 后续可以同时覆盖 Android 和 iOS

## 2.2 本地数据库

推荐使用：

- Drift
- SQLite

理由：
- 类型安全，适合维护明确的数据模型
- 支持迁移，后续字段扩展成本可控
- 查询、事务、聚合能力足够覆盖本产品
- 比纯 key-value 更适合活动记录、生活日状态、重算和趋势查询

## 2.3 状态管理

推荐使用：

- Riverpod
- Riverpod code generation 可选

理由：
- 适合把页面状态、数据库流、领域服务组合起来
- 易于测试
- 对异步状态、生命周期和依赖注入支持较好
- 不需要引入过重的架构框架

## 2.4 其他建议依赖

建议：
- `freezed`：定义不可变领域对象和 union 状态
- `json_serializable`：配置、导出、模型序列化
- `go_router`：页面路由
- `intl`：日期和本地化格式

可暂缓：
- 复杂图表库。第一版趋势展示简单，可先用基础组件或轻量自绘。
- 后台任务库。第一版生活日结算可在 App 启动和回到前台时触发。

# 3. 总体架构

第一版采用本地单体分层架构：

```text
UI Layer
  页面 / 组件 / 手势 / 动画

State Layer
  Riverpod providers
  页面状态、启动状态、提示状态、异步加载状态

Application Layer
  用例编排
  启动准备、记录活动、撤销、补做早间、生活日结算、周调整

Domain Layer
  精力计算、生活日规则、有效使用日判断、标签生成、校准规则

Data Layer
  Drift DAOs
  SQLite tables
  配置、记录、每日状态、模型、反馈
```

核心原则：
- UI 不直接写数据库。
- UI 不直接计算精力影响。
- 所有业务写操作通过 Application Service 完成。
- Domain Service 保持纯函数优先，方便单元测试。
- 数据变更后通过 Riverpod 刷新页面状态。

# 5. 核心数据模型

## 5.1 ActivityRecord

用途：保存每次活动记录。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| lifeDay | String | 生活日，建议 `yyyy-MM-dd` |
| startedAt | DateTime | 估算开始时间，`completedAt - duration` |
| completedAt | DateTime | 记录完成时间，也是第一版生活日归属依据 |
| category | String | 大类 |
| subcategory | String | 子类 |
| durationMinutes | int | 固定档位 |
| theoreticalDelta | int | 理论变化值 |
| appliedDelta | int | 实际应用值 |
| status | String | `active` / `cancelled` |
| feedbackId | String? | 关联抽样反馈 |
| cancelledAt | DateTime? | 撤销时间 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

关键约束：
- 默认业务查询只查 `status = active`
- 撤销只改状态，不物理删除
- 重算时刷新 `active` 记录的 `appliedDelta`

## 5.2 DailyEnergyState

用途：保存每个生活日的结算和实时状态。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| lifeDay | String | 主键 |
| initialEnergy | int | 当日初始精力 |
| baseEnergy | int | 当时使用的个人基准线 |
| morningAdjustment | int | 早间微调 |
| shortTermAdjustment | int | 短期修正 |
| currentEnergy | int | 当前剩余精力 |
| finalEnergy | int? | 结算后的最终剩余精力 |
| totalConsumption | int | 总消耗，正数存储 |
| totalRecovery | int | 总恢复，正数存储 |
| isStandardEffectiveDay | bool | 标准有效使用日 |
| isWeakEffectiveDay | bool | 弱有效使用日 |
| isSettled | bool | 是否已结算 |
| recalculatedByRuleChange | bool | 是否因规则变更重算 |
| reminderFlags | String | JSON，记录中低 / 低 / 透支是否提醒过 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

## 5.3 MorningCheckIn

用途：保存每个生活日的早间确认。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| lifeDay | String | 生活日 |
| overallState | String | `bad` / `normal` / `good` |
| freeTimeLevel | String | `low` / `medium` / `high` |
| pressureSource | String | `study` / `practice` / `both` / `low` |
| adjustment | int | 早间微调值 |
| completedAt | DateTime | 完成时间 |
| isDefaultQuickStart | bool | 是否首次默认快速开始 |

约束：
- 每个生活日最多一条有效早间确认。
- 补做早间确认后，需要重算当日初始精力和当日记录的 `appliedDelta`。

## 5.4 UserEnergyModel

用途：保存用户长期模型和设置。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 固定单行 |
| baseEnergy | int | 个人基准线，默认 100 |
| dynamicLearningEnabled | bool | 动态学习开关 |
| onboardingCompleted | bool | 新手引导是否完成 |
| calibrationEffectiveDayCount | int | 当前校准周期进度 |
| lastAdjustmentLifeDay | String? | 上次周调整处理的生活日 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

约束：
- `baseEnergy` 手动调整范围 60 到 140。
- 单次调整超过 16 需要二次确认。

## 5.5 SubcategoryPersonalOffset

用途：保存每个子类的个人修正值。

| 字段 | 类型 | 说明 |
|---|---|---|
| subcategory | String | 子类 |
| offset | int | 范围 -6 到 +6 |
| updatedAt | DateTime | 更新时间 |

## 5.6 CalibrationFeedback

用途：保存校准期抽样反馈。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| activityRecordId | String | 对应活动 |
| lifeDay | String | 生活日 |
| subcategory | String | 子类 |
| direction | String | `tooLight` / `aboutRight` / `tooHeavy` |
| status | String | `active` / `invalidated` |
| createdAt | DateTime | 创建时间 |

约束：
- 如果活动记录被撤销，对应反馈自动变为 `invalidated`。
- 参数更新只使用 `status = active` 的反馈。

## 5.7 PromptState

用途：保存提示关闭、展示、延后状态。

可选实现：
- 单独表 `prompt_states`
- 或放在 `DailyEnergyState.reminderFlags` 和 `UserEnergyModel` 中

建议第一版单独建表，降低提示状态互相污染。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| lifeDay | String? | 与生活日相关的提示 |
| type | String | `morning` / `yesterday` / `weeklyAdjustment` / `calibrationDone` / `energyReminder` |
| status | String | `pending` / `shown` / `dismissed` / `deferred` |
| shownAt | DateTime? | 展示时间 |
| dismissedAt | DateTime? | 关闭时间 |

# 6. 核心领域服务

## 6.1 LifeDayService

职责：
- 根据当前时间计算生活日
- 判断时间是否跨过 04:00
- 将记录完成时间映射到生活日

规则：

```text
如果本地时间 hour < 4：
  lifeDay = 前一个自然日
否则：
  lifeDay = 当前自然日
```

第一版记录归属以 `completedAt` 为准。

## 6.2 EnergyCalculator

职责：
- 计算当日初始精力
- 计算活动理论变化值
- 根据恢复上限计算实际应用值
- 计算低精力 / 透支档位

关键函数：

```text
calculateInitialEnergy(baseEnergy, morningAdjustment, shortTermAdjustment)
calculateTheoreticalDelta(subcategory, durationMinutes, personalOffset)
calculateAppliedDelta(theoreticalDelta, currentEnergy, initialEnergy)
getEnergyBand(currentEnergy, initialEnergy)
```

## 6.3 ReplayService

职责：
- 按事件流重放一个生活日
- 重新计算每条 `active` 记录的 `appliedDelta`
- 刷新 DailyEnergyState 的当前值、总消耗、总恢复、有效使用日状态

重放流程：

```text
energy = initialEnergy
for record in activeRecords sorted by completedAt:
  theoreticalDelta = calculateTheoreticalDelta(...)
  appliedDelta = calculateAppliedDelta(theoreticalDelta, energy, initialEnergy)
  update record.appliedDelta
  energy += appliedDelta

update daily.currentEnergy
update totalConsumption / totalRecovery
update effective day flags
```

触发场景：
- 新增活动记录
- 撤销活动记录
- 补做早间确认
- 修改活动默认规则
- 修改个人基准线并影响当天
- 最近 7 个有效使用日重算

## 6.4 SettlementService

职责：
- 处理待结算生活日
- 多日未打开时从旧到新逐日结算
- 空生活日不生成 DailyEnergyState
- 生成昨日总结和趋势所需数据

启动时调用：

```text
pendingLifeDays = findUnsettledLifeDaysBefore(currentLifeDay)
for lifeDay in pendingLifeDays ordered asc:
  replay(lifeDay)
  markSettled(lifeDay)
```

## 6.5 ReminderService

职责：
- 判断中低精力、低精力、透支提醒
- 保证同一生活日同一档位只提醒一次
- 用户关闭当前提示后不再展示
- 补做早间确认后只向更轻方向撤回，不触发更重档位新提醒

## 6.6 CalibrationService

职责：
- 统计有效使用日
- 处理校准期抽样反馈
- 每 7 个有效使用日生成个人基准线建议
- 更新子类个人修正值
- 动态学习关闭时不生成趋势调整建议

## 6.7 YesterdayLabelService

职责：
- 根据生活日结算数据生成昨日标签
- 使用固定标签库
- 按优先级最多取 3 个
- 无特殊标签命中时兜底展示“整体稳定”

# 7. Application Services

## 7.1 AppStartupService

App 启动或回到前台时执行：

1. 获取当前时间和当前生活日
2. 初始化用户模型，若不存在则创建默认模型
3. 调用 SettlementService 处理待结算生活日
4. 确保当前生活日 DailyEnergyState 存在
5. 判断新手引导、昨日总结、早间确认、周调整提示状态
6. 输出首页初始化状态

提示顺序：
1. 新手引导
2. 昨日总结提示
3. 早间确认
4. 周调整提示

## 7.2 ActivityRecordService

记录活动流程：

1. 根据 `completedAt` 计算生活日
2. 确保对应 DailyEnergyState 存在
3. 根据子类、时长、个人修正值计算 `theoreticalDelta`
4. 计算 `appliedDelta`
5. 写入 ActivityRecord
6. 调用 ReplayService 重放当天，刷新当日状态
7. 生成记录完成反馈
8. 判断是否需要低精力提醒
9. 如果符合条件，在 5 秒撤销条结束后再展示抽样反馈

## 7.3 CancelActivityService

撤销流程：

1. 校验记录仍在 5 秒撤销窗口内
2. 将 ActivityRecord.status 改为 `cancelled`
3. 写入 `cancelledAt`
4. 将关联 CalibrationFeedback 置为 `invalidated`
5. 调用 ReplayService 重放当天
6. 刷新首页、今日概览、有效使用日状态

## 7.4 MorningCheckInService

早间确认流程：

1. 写入或更新当天 MorningCheckIn
2. 计算 morningAdjustment
3. 更新 DailyEnergyState.initialEnergy
4. 调用 ReplayService 重放当天，刷新所有 `active` 记录的 `appliedDelta`
5. 如果原本是弱有效使用日，重新判断是否升级为标准有效使用日
6. 更新提醒状态：只撤回更轻方向，不触发更重档位新提醒

## 7.5 WeeklyAdjustmentService

周调整流程：

1. 判断是否累计 7 个有效使用日
2. 如果动态学习关闭，跳过生成建议
3. 读取最近 7 个有效使用日结算数据
4. 生成个人基准线调整建议
5. 生成轻量原因摘要
6. 用户同意后更新 UserEnergyModel.baseEnergy
7. 用户拒绝后保持原值
8. 记录本次处理状态，避免重复强提示

# 9. 能量球手势实现方案

第一版推荐实现为一个独立 `RecordGestureController`。

状态机：

```text
idle
  -> selectingCategory
  -> selectingSubcategory
  -> selectingDuration
  -> completed
  -> cancelled
```

规则：
- 只有在 `selectingDuration` 状态松手才完成记录。
- 其他状态松手均取消。
- 回滑按层级回退：时间档位 -> 子类 -> 大类 -> 取消。
- 进入某层后 10 秒无动作自动取消。
- 第一版不校验记录之间的时间重叠。

UI 建议：
- 手势状态只生成临时选择，不写数据库。
- 松手确认后才调用 ActivityRecordService。
- 完成后显示 5 秒反馈条和撤销入口。
- 抽样反馈必须等 5 秒撤销条结束后再出现。

  -> recalculate initialEnergy
  -> ReplayService.replayLifeDay()
  -> update reminder state
  -> Home refresh

# 11. 事务边界

以下操作必须放在数据库事务中：

- 创建活动记录 + 重放当天 + 更新 DailyEnergyState
- 撤销活动记录 + 作废反馈 + 重放当天
- 补做早间确认 + 更新初始精力 + 重放当天
- 规则变更 + 最近 7 个有效使用日重算
- 用户确认周调整 + 更新个人基准线 + 写入处理状态

原因：
- 避免首页数值、概览、记录状态不一致
- 避免 App 中途退出后留下半更新状态
- 保证测试可验证

# 12. 测试方案

## 12.1 Domain 单元测试

必须覆盖：
- 生活日 04:00 切换
- 当日初始精力计算
- 透支短期修正
- 恢复上限
- `theoreticalDelta` / `appliedDelta`
- 事件流重放
- 有效使用日判定
- 今日概览排序
- 昨日标签生成
- 7 个有效使用日统计
- 子类个人修正值更新阈值

## 12.2 Application 测试

必须覆盖：
- 记录活动后首页状态更新
- 5 秒内撤销后业务上视为未发生
- 撤销记录不参与校准和模型学习
- 补做早间确认后刷新 `appliedDelta`
- 多日未打开 App 后逐日结算
- 动态学习关闭后不生成周调整建议
- 周调整用户同意 / 拒绝两条路径

## 12.3 Widget 测试

建议覆盖：
- 新手引导完成 / 跳过
- 早间确认完成 / 跳过
- 首页低精力提示关闭
- 记录完成反馈条
- 昨日提示展开
- 设置中手动基准线范围校验

## 12.4 手动验收场景

必须手动走通：
- 新用户首次打开完整流程
- 一天内记录消耗、恢复、撤销
- 恢复上限截断文案
- 当天透支，第二天初始精力轻微下调
- 跳过早间后记录 2 次形成弱有效使用日
- 补做早间后升级为标准有效使用日
- 累计 7 个有效使用日后出现周调整

# 14. 风险与处理策略

## 14.1 能量球手势实现复杂

风险：
- 手势层级、回滑、吸附、取消状态容易出现边界 bug。

策略：
- 先实现可用状态机，再做动效。
- 手势控制器独立测试。
- 备用记录入口保留，降低新手和误操作风险。

## 14.2 `appliedDelta` 与重算一致性

风险：
- 补做早间、规则变更、撤销后，如果没有重放，会出现当前精力和记录不一致。

策略：
- 所有影响当日状态的写操作统一调用 ReplayService。
- 不允许各页面自行累加精力。
- 关键流程放在事务中。

## 14.3 提示过多

风险：
- 新手引导、昨日总结、早间确认、周调整可能同时出现。

策略：
- 启动统一由 AppStartupService 编排。
- 提示状态持久化。
- 周调整作为独立卡片或页面，不抢在昨日总结前。

## 14.4 本地数据丢失

风险：
- 第一版无账号和云同步，卸载或换机数据会丢失。

策略：
- 设置页明确本地数据提示。
- 提供 P2 JSON 导出。
- 数据结构保持可序列化，为后续云同步预留。

# 15. 技术待确认项

进入开发前建议确认：

- Flutter 最低支持系统版本
- 目标平台先 Android 还是 Android + iOS
- 设计稿是否先做低保真交互稿
- 默认活动精力规则的具体配置表是否单独成文
- Drift 表结构是否需要先生成 ER 图
- 是否需要在第一版加入简单 debug 面板，方便查看生活日、记录、精力重放结果

---

# 16. 推荐结论

第一版最稳妥的技术路线是：

> Flutter + Riverpod + Drift + SQLite，本地离线优先，核心业务规则沉到 Domain / Application 层，通过事件流重放保证精力计算一致性。

这个方案的优势：
- 能支撑能量球这种强交互首页
- 能保证本地数据和计算结果稳定
- 能让核心算法脱离 UI 独立测试
- 后续扩展云同步、单条记录详情、复杂趋势分析时不需要推翻重做
