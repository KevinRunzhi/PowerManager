# 1. 技术目标

第一版技术目标：

- 离线可用，不依赖账号、云同步和服务端
- 精力计算结果稳定、可追溯、可重算
- 活动记录、撤销、生活日结算、校准等核心流程可单元测试
- UI 层尽量只负责展示和交互，不直接承载业务规则
- 本地数据结构支持后续版本扩展，如单条记录详情、云同步、更多趋势分析

第一版不追求：
- 服务端架构
- 多端同步
- 复杂机器学习
- 实时后台任务
- 高度复杂的图表能力

# 2. 推荐技术栈

## 2.1 客户端框架

推荐使用：

- Flutter
- Dart
- Material 3 或自定义轻量设计系统

理由：
- 适合移动端单体应用
- 手势、自定义绘制、动画能力较强，适合能量球交互
- 本地数据库、状态管理、测试工具链成熟
- 后续可以同时覆盖 Android 和 iOS

## 2.2 本地数据库

推荐使用：

- Drift
- SQLite

理由：
- 类型安全，适合维护明确的数据模型
- 支持迁移，后续字段扩展成本可控
- 查询、事务、聚合能力足够覆盖本产品
- 比纯 key-value 更适合活动记录、生活日状态、重算和趋势查询

## 2.3 状态管理

推荐使用：

- Riverpod
- Riverpod code generation 可选

理由：
- 适合把页面状态、数据库流、领域服务组合起来
- 易于测试
- 对异步状态、生命周期和依赖注入支持较好
- 不需要引入过重的架构框架

## 2.4 其他建议依赖

建议：
- `freezed`：定义不可变领域对象和 union 状态
- `json_serializable`：配置、导出、模型序列化
- `go_router`：页面路由
- `intl`：日期和本地化格式

可暂缓：
- 复杂图表库。第一版趋势展示简单，可先用基础组件或轻量自绘。
- 后台任务库。第一版生活日结算可在 App 启动和回到前台时触发。

# 3. 总体架构

第一版采用本地单体分层架构：

```text
UI Layer
  页面 / 组件 / 手势 / 动画

State Layer
  Riverpod providers
  页面状态、启动状态、提示状态、异步加载状态

Application Layer
  用例编排
  启动准备、记录活动、撤销、补做早间、生活日结算、周调整

Domain Layer
  精力计算、生活日规则、有效使用日判断、标签生成、校准规则

Data Layer
  Drift DAOs
  SQLite tables
  配置、记录、每日状态、模型、反馈
```

核心原则：
- UI 不直接写数据库。
- UI 不直接计算精力影响。
- 所有业务写操作通过 Application Service 完成。
- Domain Service 保持纯函数优先，方便单元测试。
- 数据变更后通过 Riverpod 刷新页面状态。

# 5. 核心数据模型

## 5.1 ActivityRecord

用途：保存每次活动记录。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| lifeDay | String | 生活日，建议 `yyyy-MM-dd` |
| startedAt | DateTime | 估算开始时间，`completedAt - duration` |
| completedAt | DateTime | 记录完成时间，也是第一版生活日归属依据 |
| category | String | 大类 |
| subcategory | String | 子类 |
| durationMinutes | int | 固定档位 |
| theoreticalDelta | int | 理论变化值 |
| appliedDelta | int | 实际应用值 |
| ruleVersion | String | 创建或规则迁移时使用的规则版本 |
| personalizationVersion | int | 个性化参数版本 |
| personalFactorSnapshot | double | 本次计算使用的子类强度倍率 |
| status | String | `active` / `cancelled` |
| cancelledAt | DateTime? | 撤销时间 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

关键约束：
- 默认业务查询只查 `status = active`
- 撤销只改状态，不物理删除
- 普通重放只刷新 `active` 记录的 `appliedDelta`，不得改变 `theoreticalDelta`
- 只有显式规则迁移重放可以刷新目标窗口内的 `theoreticalDelta` 和规则版本
- 重放稳定顺序为 `completedAt, createdAt, id`

## 5.2 DailyEnergyState

用途：保存每个生活日的结算和实时状态。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| lifeDay | String | 主键 |
| initialEnergy | int | 当日初始精力 |
| baseEnergy | int | 当时使用的个人基准线 |
| morningAdjustment | int | 早间微调 |
| shortTermAdjustment | int | 短期修正 |
| currentEnergy | int | 当前剩余精力 |
| finalEnergy | int? | 结算后的最终剩余精力 |
| totalConsumption | int | 总消耗，正数存储 |
| totalRecovery | int | 总恢复，正数存储 |
| isStandardEffectiveDay | bool | 标准有效使用日 |
| isWeakEffectiveDay | bool | 弱有效使用日 |
| isSettled | bool | 是否已结算 |
| recalculatedByRuleChange | bool | 是否因规则变更重算 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

## 5.3 MorningCheckIn

用途：保存每个生活日的早间确认。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| lifeDay | String | 生活日 |
| overallState | String | `bad` / `normal` / `good` |
| freeTimeLevel | String | `low` / `medium` / `high` |
| pressureSource | String | `study` / `practice` / `both` / `low` |
| adjustment | int | 早间微调值 |
| completedAt | DateTime | 完成时间 |
| isDefaultQuickStart | bool | 是否首次默认快速开始 |

约束：
- `lifeDay` 唯一，每个生活日最多一条早间确认。
- 补做早间确认后，需要重算当日初始精力和当日记录的 `appliedDelta`。

## 5.4 UserEnergyModel

用途：保存用户长期模型和设置。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 固定单行 |
| baseEnergy | int | 个人基准线，默认 100 |
| pendingBaseEnergy | int? | 等待下一个生活日生效的基准线 |
| baseEnergyEffectiveLifeDay | String? | 待生效生活日 |
| dynamicLearningEnabled | bool | 动态学习开关 |
| onboardingCompleted | bool | 新手引导是否完成 |
| personalizationVersion | int | 当前个性化参数版本 |
| activeRuleVersion | String | 当前默认规则版本 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

约束：
- `baseEnergy` 手动调整范围 60 到 140。
- 单次调整超过 16 需要二次确认。
- 基准线修改不重算当前生活日；OperationPreparationService 在目标生效生活日原子应用 pendingBaseEnergy。

## 5.5 SubcategoryPersonalFactor

用途：保存每个子类的个人影响强度倍率。

| 字段 | 类型 | 说明 |
|---|---|---|
| subcategory | String | 子类 |
| factor | double | 默认 1.00，范围 0.70 到 1.30 |
| version | int | 个性化参数版本 |
| updatedAt | DateTime | 更新时间 |

## 5.6 CalibrationFeedback

用途：保存校准期抽样反馈。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| activityRecordId | String | 对应活动 |
| lifeDay | String | 生活日 |
| subcategory | String | 子类 |
| direction | String | `tooLight` / `aboutRight` / `tooHeavy` |
| status | String | `active` / `invalidated` |
| createdAt | DateTime | 创建时间 |

约束：
- 如果活动记录被撤销，对应反馈自动变为 `invalidated`。
- 参数更新只使用 `status = active` 的反馈。
- `activityRecordId` 唯一，一条活动最多一条有效反馈。

## 5.7 CalibrationCycle

用途：保存非重叠的 7 有效使用日周期及周调整决策。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| sequence | int | 周期序号，唯一 |
| startedLifeDay | String? | 第一个有效生活日 |
| completedLifeDay | String? | 第 7 个有效生活日 |
| effectiveDayIds | String | 冻结的生活日列表，JSON |
| status | String | `collecting / pending / accepted / rejected / deferred / noChange / invalidated` |
| baseEnergyBefore | int? | 生成建议时的基准线 |
| suggestedBaseEnergy | int? | 建议值 |
| algorithmVersion | String | 校准算法版本 |
| decidedAt | DateTime? | 用户处理时间 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |

约束：
- 同时最多一个 `collecting` 周期。
- 同一个周期只能有一个未失效建议。
- 第 7 个有效日结算后冻结 `effectiveDayIds`，后续有效日进入下一周期。

## 5.8 PromptState

用途：保存提示关闭、展示、延后状态。

第一版固定使用独立 `prompt_states` 表，避免提示状态分散和双写。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | UUID |
| scopeKey | String | 业务去重键 |
| lifeDay | String? | 与生活日相关的提示 |
| calibrationCycleId | String? | 与校准周期相关的提示 |
| type | String | `morning` / `yesterday` / `weeklyAdjustment` / `calibrationDone` / `energyReminder` |
| status | String | `pending` / `shown` / `dismissed` / `deferred` |
| shownAt | DateTime? | 展示时间 |
| dismissedAt | DateTime? | 关闭时间 |

约束：
- `type + scopeKey` 唯一。
- 精力提醒的 scopeKey 为 `lifeDay + band`。
- 昨日或上次记录日提示的 scopeKey 为目标生活日。
- 周调整提示的 scopeKey 为 CalibrationCycle.id。
- PromptState 是提示状态的唯一持久化来源，不在 DailyEnergyState 重复保存 reminderFlags。

## 5.9 ActivityRuleConfigVersion

用途：保存内置或用户修改后的活动规则版本。

| 字段 | 类型 | 说明 |
|---|---|---|
| version | String | 主键，例如 `energy-rules-v1` |
| valuesJson | String | 20 × 6 levelKey 矩阵、等级数值映射和早间、提醒、抽样参数 |
| source | String | `bundled / userModified` |
| createdAt | DateTime | 创建时间 |

约束：
- 内置 v1 内容与《精力值规则配置 v1》一致。
- 已被 ActivityRecord 引用的版本不可原地修改。
- 用户修改规则时创建新版本，并通过 ruleMigrationReplay 显式迁移目标窗口。
- 等级映射必须保持恢复为正、消耗为负、同方向强度单调，neutral 固定为 0。

# 6. 核心领域服务

## 6.1 LifeDayService

职责：
- 根据当前时间计算生活日
- 判断时间是否跨过 04:00
- 将记录完成时间映射到生活日

规则：

```text
如果本地时间 hour < 4：
  lifeDay = 前一个自然日
否则：
  lifeDay = 当前自然日
```

第一版记录归属以 `completedAt` 为准。

时间戳以 UTC 保存；`lifeDay` 在记录创建时按设备本地时区计算后持久化。用户切换时区时不重新归属历史记录。

## 6.2 EnergyCalculator

职责：
- 计算当日初始精力
- 计算活动理论变化值
- 根据恢复上限计算实际应用值
- 计算低精力 / 透支档位

关键函数：

```text
calculateInitialEnergy(baseEnergy, morningAdjustment, shortTermAdjustment)
calculateTheoreticalDelta(subcategory, durationMinutes, personalFactor, ruleVersion)
calculateAppliedDelta(theoreticalDelta, currentEnergy, initialEnergy)
getEnergyBand(currentEnergy, initialEnergy)
```

## 6.3 ReplayService

职责：
- 按事件流重放一个生活日
- 在普通重放和规则迁移重放之间建立明确边界
- 刷新 DailyEnergyState 的当前值、总消耗、总恢复、有效使用日状态

普通重放 `operationalReplay`：

```text
energy = initialEnergy
for record in activeRecords sorted by completedAt, createdAt, id:
  appliedDelta = calculateAppliedDelta(record.theoreticalDelta, energy, initialEnergy)
  update record.appliedDelta
  energy += appliedDelta

update daily.currentEnergy
update totalConsumption = sum(abs(appliedDelta)) where appliedDelta < 0
update totalRecovery = sum(appliedDelta) where appliedDelta > 0
update effective day flags
```

规则迁移重放 `ruleMigrationReplay`：

```text
for lifeDay in affectedLifeDays ordered asc:
  recalculate shortTermAdjustment when the previous calendar lifeDay is also in scope
  for record in activeRecords sorted by completedAt, createdAt, id:
    theoreticalDelta = calculateTheoreticalDelta(..., record.personalFactorSnapshot, targetRuleVersion)
    update record.theoreticalDelta / ruleVersion
    recalculate appliedDelta
  update daily aggregates
```

规则迁移窗口为当前未结算生活日和最近 7 个有效使用日。窗口起点之前的 initialEnergy 与 shortTermAdjustment 作为固定输入；空生活日中断短期修正传播。

触发场景：
- 新增、撤销、补做早间：`operationalReplay`
- 用户确认修改默认规则：`ruleMigrationReplay`
- 个人基准线修改不重放当前生活日，从决策发生时所属生活日的下一个生活日起生效

## 6.4 SettlementService

职责：
- 处理待结算生活日
- 多日未打开时从旧到新逐日结算
- 空生活日不生成 DailyEnergyState；每日状态延迟到首次早间确认或首次活动记录时创建
- 生成昨日或上次记录日总结和趋势所需数据

启动时调用：

```text
pendingLifeDays = findUnsettledLifeDaysBefore(currentLifeDay)
for lifeDay in pendingLifeDays ordered asc:
  operationalReplay(lifeDay)
  markSettled(lifeDay)
```

SettlementService 由统一的 `OperationPreparationService` 调用。所有业务写操作在开始前都必须执行状态准备，使 App 持续前台跨过 04:00 时也能正确结算。

## 6.5 ReminderService

职责：
- 判断中低精力、低精力、透支提醒
- 保证同一生活日同一档位只提醒一次
- 用户关闭当前提示后不再展示
- 补做早间确认后只向更轻方向撤回，不触发更重档位新提醒
- 一次跨过多个档位时只展示最高严重度，并把较轻档位标记为已处理
- 精力提醒等待 5 秒撤销窗口结束后再持久化和展示
- PromptState 是提示状态的唯一持久化来源

档位按 `overdraft -> low -> mediumLow -> normal` 顺序判断并在首次命中时停止：

```text
currentEnergy < 0                    -> overdraft
currentEnergy < initialEnergy * .25 -> low
currentEnergy < initialEnergy * .50 -> mediumLow
otherwise                            -> normal
```

## 6.6 CalibrationService

职责：
- 统计有效使用日
- 处理校准期抽样反馈
- 每 7 个有效使用日生成个人基准线建议
- 更新子类 personalFactor 和个性化参数版本
- 动态学习关闭时不生成趋势调整建议
- 动态学习关闭时使 pending / deferred 周期建议失效，并停止相关 PromptState
- 管理非重叠 CalibrationCycle，并在第 7 个有效日结算后冻结周期输入
- 按《精力值规则配置 v1》的确定性公式生成建议
- 使用 personalFactor 更新影响强度，禁止改变默认规则的正负方向

## 6.7 YesterdayLabelService

职责：
- 根据生活日结算数据生成昨日标签
- 使用固定标签库
- 按优先级最多取 3 个
- 无特殊标签命中时兜底展示“整体稳定”

# 7. Application Services

## 7.0 OperationPreparationService

所有业务写操作和启动 / 回前台共用：

1. 根据当前时间计算目标生活日。
2. 从旧到新结算目标生活日之前的未结算状态。
3. 如果目标生活日达到 `baseEnergyEffectiveLifeDay`，原子应用 pendingBaseEnergy。
4. 返回目标生活日上下文。
5. 不主动持久化空的 DailyEnergyState。

该服务必须幂等，重复调用不得重复结算、重复创建每日状态或重复推进校准周期。

## 7.1 AppStartupService

App 启动或回到前台时执行：

1. 初始化用户模型，若不存在则创建默认模型
2. 调用 OperationPreparationService 处理生活日和待结算状态
3. 从持久化状态或默认内存值构造首页状态，不创建空 DailyEnergyState
4. 判断新手引导、昨日或上次记录日总结、早间确认、周调整提示状态
5. 输出首页初始化状态

提示顺序：
1. 新手引导
2. 昨日或上次记录日总结提示
3. 早间确认
4. 周调整提示

## 7.2 ActivityRecordService

记录活动流程：

1. 调用 OperationPreparationService
2. 延迟创建或读取对应 DailyEnergyState
3. 根据子类、时长、规则版本和 personalFactor 计算 `theoreticalDelta`
4. 写入带规则与个性化快照的 ActivityRecord
5. 调用 ReplayService.operationalReplay 重放当天
6. 生成记录完成反馈和 5 秒撤销入口
7. 撤销窗口结束且记录仍为 active 后，持久化最高严重度精力提醒
8. 如果符合抽样条件，再展示抽样反馈

## 7.3 CancelActivityService

撤销流程：

1. 校验记录仍在 5 秒撤销窗口内
2. 将 ActivityRecord.status 改为 `cancelled`
3. 写入 `cancelledAt`
4. 将关联 CalibrationFeedback 置为 `invalidated`
5. 调用 ReplayService.operationalReplay 重放当天
6. 刷新首页、今日概览、有效使用日状态

## 7.4 MorningCheckInService

早间确认流程：

1. 调用 OperationPreparationService
2. 写入当天唯一的 MorningCheckIn，并按规则配置计算 morningAdjustment
3. 延迟创建或更新 DailyEnergyState.initialEnergy
4. 调用 ReplayService.operationalReplay，使用已保存的 theoreticalDelta 刷新 appliedDelta
5. 如果原本是弱有效使用日，重新判断是否升级为标准有效使用日
6. 更新提醒状态：只撤回更轻方向，不触发更重档位新提醒

## 7.5 WeeklyAdjustmentService

周调整流程：

1. 读取或创建唯一的 collecting CalibrationCycle
2. 判断是否累计 7 个有效使用日
3. 如果动态学习关闭，不推进校准周期并跳过生成建议
4. 第 7 日结算后冻结 effectiveDayIds
5. 更新满足阈值的 personalFactor；发生变化时创建新的 personalizationVersion，只影响后续记录
6. 按 calibration-v1 生成个人基准线建议和原因摘要
7. 建议变化为 0 时将周期标记为 noChange，只展示结果摘要
8. 其他建议由用户接受、拒绝或延后，并更新周期状态
9. 接受后写入 UserEnergyModel.pendingBaseEnergy 和 baseEnergyEffectiveLifeDay，在决策所属生活日的下一个生活日生效
10. 创建下一个 collecting 周期，避免后续有效日污染已冻结周期

# 9. 能量球手势实现方案

第一版推荐实现为一个独立 `RecordGestureController`。

状态机：

```text
idle
  -> selectingCategory
  -> selectingSubcategory
  -> selectingDuration
  -> completed
  -> cancelled
```

规则：
- 只有在 `selectingDuration` 状态松手才完成记录。
- 其他状态松手均取消。
- 回滑按层级回退：时间档位 -> 子类 -> 大类 -> 取消。
- 进入某层后 10 秒无动作自动取消。
- 第一版不校验记录之间的时间重叠。

UI 建议：
- 手势状态只生成临时选择，不写数据库。
- 松手确认后才调用 ActivityRecordService。
- 完成后显示 5 秒反馈条和撤销入口。
- 抽样反馈必须等 5 秒撤销条结束后再出现。

# 11. 事务边界

以下操作必须放在数据库事务中：

- 状态准备 + 待结算生活日逐日结算
- 创建活动记录 + 重放当天 + 更新 DailyEnergyState
- 撤销活动记录 + 作废反馈 + 重放当天
- 补做早间确认 + 更新初始精力 + 重放当天
- 规则版本变更 + 目标窗口按生活日执行规则迁移重放
- 冻结第 7 个有效日 + 生成周期建议 + 创建 PromptState
- 用户处理周调整 + 更新周期状态 + 更新个人基准线

原因：
- 避免首页数值、概览、记录状态不一致
- 避免 App 中途退出后留下半更新状态
- 保证测试可验证

# 14. 风险与处理策略

## 14.1 能量球手势实现复杂

风险：
- 手势层级、回滑、吸附、取消状态容易出现边界 bug。

策略：
- 先实现可用状态机，再做动效。
- 手势控制器独立测试。
- 备用记录入口保留，降低新手和误操作风险。

## 14.2 `appliedDelta` 与重算一致性

风险：
- 如果普通重放重新套用当前规则，会静默改写历史 theoreticalDelta；如果撤销不重放，又会因恢复上限产生错误。

策略：
- 新增、撤销和补做早间统一调用 operationalReplay，只重算 appliedDelta。
- 只有显式规则迁移调用 ruleMigrationReplay，并写入规则版本。
- 不允许各页面自行累加精力。
- 关键流程放在事务中。

## 14.3 提示过多

风险：
- 新手引导、昨日总结、早间确认、周调整可能同时出现。

策略：
- 启动统一由 AppStartupService 编排。
- 提示状态持久化。
- 周调整作为独立卡片或页面，不抢在昨日总结前。

## 14.4 本地数据丢失

风险：
- 第一版无账号和云同步，卸载或换机数据会丢失。

策略：
- 设置页明确本地数据提示。
- 提供 P2 JSON 导出。
- 数据结构保持可序列化，为后续云同步预留。

# 16. 推荐结论

第一版最稳妥的技术路线是：

> Flutter + Riverpod + Drift + SQLite，本地离线优先，核心业务规则沉到 Domain / Application 层，通过事件流重放保证精力计算一致性。

这个方案的优势：
- 能支撑能量球这种强交互首页
- 能保证本地数据和计算结果稳定
- 能让核心算法脱离 UI 独立测试
- 后续扩展云同步、单条记录详情、复杂趋势分析时不需要推翻重做
