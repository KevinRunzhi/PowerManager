# 1. 总体目标

交付一个可以由项目作者本人连续使用 7 天的 Android MVP-A：

1. 系统显示可解释的估计精力。
2. 用户可以记录、补记、编辑和删除当前生活日活动。
3. 用户实际状态与系统估计分开保存。
4. 当前日由源数据派生，04:00 后生成不可变摘要。
5. 点击式记录入口稳定可用。
6. 能量球手势经过独立真机验证后再决定是否成为默认入口。
7. 本地数据可导出。
8. 不实现自动基准线学习、personalFactor、CalibrationCycle 或历史规则迁移。

# 2. 全局开发规则

## 2.1 每阶段完成定义

一个阶段只有同时满足以下条件才允许关闭：

- 代码完成且无调试残留。
- 对应自动化测试通过。
- 相关失败路径有明确行为。
- Android 模拟器主流程通过。
- 数据库变更有迁移测试。
- 文档与实际实现一致。
- `flutter analyze` 无错误。
- 相关 `flutter test` 通过。
- 阶段验收清单逐项记录结果。

## 2.2 质量门禁

每个阶段至少执行：

```text
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
```

涉及 Drift 时额外执行代码生成与迁移测试。

涉及 Android 集成时额外执行：

```text
flutter build apk --debug
flutter run -d emulator-5554
```

## 2.3 范围控制

开发过程中禁止顺手加入：

- 自动学习
- 高级规则编辑
- 账号与同步
- 自定义活动名称
- 历史编辑
- 复杂图表
- AI 建议
- Web 或 Windows 桌面适配

发现新需求时先记入延期清单，不直接扩大当前阶段。

## 2.4 可测试性要求

- 时间必须通过 `Clock` 抽象注入。
- 生活日边界不得直接散落使用 `DateTime.now()`。
- 规则配置必须可由测试加载。
- Domain 层不得依赖 Flutter Widget 或 Drift。
- Application 层通过 Repository 接口工作。
- UI 不直接调用 DAO。

# 6. 阶段 2：领域规则与纯算法

## 6.1 目标

在不连接 UI 和数据库的情况下，实现所有可确定的业务规则。

## 6.2 开发步骤

1. 定义稳定枚举：

- 4 个 Category
- 24 个 Subcategory
- 6 个 DurationSlot
- MorningOverallState
- SleepRecovery
- AbsoluteEnergyState
- RelativeCorrection
- EstimatedEnergyBand

2. 实现 `LifeDay` 值对象。
3. 实现可注入 `Clock`。
4. 实现 `LifeDayCalculator`：

```text
04:00 前归前一生活日
04:00 起归当前生活日
```

5. 将 24 × 6 规则编码为版本化配置。
6. 实现规则完整性校验：

- 无重复子类
- 每个子类恰好 6 个档位
- 总计 144 个单元格
- ruleVersion 不为空

7. 实现 `EnergyCalculator`：

- 初始估计
- theoreticalDelta
- 恢复上限
- 估计档位
- 短期透支修正

8. 实现稳定重放纯函数。
9. 实现分类净变化、绝对变化总量和时长汇总。
10. 实现标准有效日和弱有效日判定。

## 6.3 必须面对的问题

### 边界时间

- `03:59:59`
- `04:00:00`
- `04:00:01`
- 月末、年末
- 本地时区改变
- 系统时钟回拨

MVP-A 历史 lifeDay 一旦持久化不重新归属。

### 恢复上限的顺序依赖

同样的恢复和消耗顺序不同，appliedDelta 可能不同。因此：

- 排序必须稳定。
- 编辑较早记录后必须重放全部当天记录。
- 禁止简单增量回滚。

### 估计与实际混淆

Domain 类型和字段命名必须使用 `Estimated` 或 `Observation`，避免继续使用含义模糊的 `energy` / `finalEnergy`。

### 浮点阈值

档位阈值涉及 25% 和 50%。优先使用整数交叉相乘，避免浮点边界误差。

## 6.4 单元测试

至少覆盖：

- 三个 04:00 边界。
- 24 × 6 规则数量与已知抽样值。
- 综合状态 `-6 / 0 / +6`。
- 短期修正五个区间。
- 空前日摘要时短期修正为 0。
- 恢复在满值时 appliedDelta 为 0。
- 恢复部分截断。
- 消耗可进入负数。
- 恰好 0、25%、50% 的档位。
- 相同 completedAt 使用 createdAt、id 决胜。
- 删除记录不参与重放。
- grossDelta 与 netDelta 分开。

## 6.5 验收标准

- Domain 测试不依赖 Flutter binding 或 SQLite。
- 144 个规则单元格验证通过。
- 重放结果在任意相同输入下确定。
- 字段命名不会把估计写成实际状态。
- 覆盖所有规则边界示例。

## 6.6 阶段退出条件

核心精力计算可以通过纯 Dart 测试证明正确。

# 7. 阶段 3：Drift 数据层

## 7.1 目标

建立七张最小表、Repository 接口和数据库约束。

## 7.2 开发步骤

按依赖顺序建立：

1. `app_settings`
2. `rule_config_versions`
3. `morning_check_ins`
4. `activity_records`
5. `energy_observations`
6. `daily_summaries`
7. `prompt_receipts`

然后：

8. 建立数据库版本 1。
9. 建立枚举字符串转换。
10. 插入唯一默认 settings 行。
11. 插入 `energy-rules-v2-mvp-a`。
12. 为每张表建立 DAO / Repository。
13. 建立事务测试工具和临时内存数据库。
14. 定义 JSON 导出 DTO，但本阶段不实现导出 UI。

## 7.3 关键约束

- `morning_check_ins.lifeDay` 唯一。
- 每个 lifeDay 最多一条 dailyAbsolute observation。
- `daily_summaries.lifeDay` 主键唯一。
- 已引用 ruleVersion 不可修改。
- activity status 只允许 active / deleted。
- 时长只允许六个固定值。
- category 与 subcategory 必须匹配。
- prompt receipt 具有稳定 scopeKey。

## 7.4 必须面对的问题

### Drift 代码生成

- 生成文件不能手工修改。
- Schema 变更必须先改表定义，再运行生成器。
- CI / 本地命令必须一致。

### DateTime 与 lifeDay

- UTC 时间戳与本地 lifeDay 分开保存。
- 不把 `yyyy-MM-dd` 当作 UTC 日期推算。
- lifeDay 推荐使用稳定字符串或专用 converter。

### 不可变摘要

数据库层需要拒绝普通 update/delete DailySummary。测试和迁移工具可以有受限入口。

### 删除语义

逻辑删除记录仍需导出，但默认业务查询必须自动过滤。

## 7.5 数据层测试

- 首次建库。
- 默认规则和 settings 初始化幂等。
- 七张表 CRUD。
- 所有唯一约束。
- 无效时长和分类组合拒绝保存。
- 逻辑删除默认过滤。
- DailySummary 重复插入失败或幂等返回。
- 事务失败完整回滚。
- 数据库关闭和重新打开后数据保留。

## 7.6 验收标准

- Schema v1 可重复创建。
- Drift 生成无警告。
- Repository 不泄漏 Drift row 到 Domain。
- 约束测试通过。
- 当前没有额外第八张业务表。

# 8. 阶段 4：当前日派生与生活日准备

## 8.1 目标

打通 `OperationPreparationService`、`CurrentDayProjector` 和 `SettlementService`。

## 8.2 开发步骤

1. 实现 CurrentDayProjector：

- 加载当天基准线和规则版本
- 加载 MorningCheckIn
- 加载前一生活日 DailySummary
- 加载当天 active records
- 调用 Domain 重放
- 返回完整 CurrentDayProjection

2. 实现应用 pendingBaseEnergy。
3. 实现应用 pendingRuleVersion。
4. 实现 SettlementService。
5. 实现 OperationPreparationService。
6. 所有写用例入口预留 `prepare()`。
7. 建立 debug 状态页面：

- 当前 UTC / 本地时间
- current lifeDay
- initial/current estimate
- ruleVersion
- 记录排序
- 前一日短期修正

## 8.3 必须面对的问题

### 结算触发

不能只依赖 App 启动。必须覆盖：

- 冷启动
- 从后台回前台
- App 持续前台跨过 04:00 后第一次写操作

### 空生活日

只有打开 App 不应生成 DailySummary。必须先判断是否存在早间确认、活动或实际观测。

### 晚到的实际状态

DailySummary 冻结计算结果；下一日补充上一日实际状态只写 energy_observations，历史页面 join 读取，不更新摘要。

### 幂等

重复 prepare 不得：

- 重复应用 pending 设置
- 重复生成摘要
- 重复创建提示回执

## 8.4 测试

- App 03:50 打开、04:10 写记录。
- 多日未打开后从旧到新结算。
- 无数据空日跳过。
- 重复 prepare 十次结果一致。
- 中途事务失败不留下半摘要。
- pending 基准线恰好下一生活日生效一次。
- pending 规则版本恰好下一生活日生效一次。

## 8.5 验收标准

- 当前日状态完全由源数据派生。
- 过去生活日最多一个摘要。
- 空日无摘要。
- 状态准备在所有写用例前复用。
- debug 页面可解释当前结果来源。

# 10. 阶段 6：早间确认与双轨状态

## 10.1 目标

实现估计与用户实际状态的独立采集和展示。

## 10.2 开发步骤

1. 建立四项早间确认 UI。
2. 允许跳过；跳过后以“个人基准线 + 上一生活日短期修正”生成估计，不加入晨间综合状态修正。
3. 跳过状态下显示弱点亮能量球、估计值和“未进行晨间确认”标签。
4. 实现首页后续补做入口。
5. 实现 SaveMorningCheckIn。
6. 补做后重放当天，并将能量球从弱点亮状态过渡到正式档位状态。
7. 实现每日五档实际状态。
8. 确保用户选择前不展示用于比较的最终估计。
9. 保存后再展示描述性差异。
10. 实现下一生活日补充上一日状态。
11. 实现随时三档校正。
12. 相对校正保存当时 estimate 快照。
13. 明确反馈不改变 MVP-A 规则。

## 10.3 必须面对的问题

### 锚定

每日实际状态确认前不能先突出显示结算估计，否则用户容易迎合系统数字。

### 迟到观测

补充上一日实际状态不能修改 DailySummary，只能新增独立 observation。

### 多次提交

dailyAbsolute 必须唯一。重复进入时应编辑/确认已有选择还是只读，需要在 UI 中明确；MVP-A 推荐当天可改，次日补充保存后只读。

### 相对校正语义

校正绑定“当时估计”，不能只保存 lower/aboutRight/higher 而缺少上下文。

## 10.4 测试

- 四项均可保存。
- 只有综合状态改变初始估计。
- 睡眠恢复感不重复计分。
- 跳过早间仍可记录。
- 跳过后估计等于个人基准线与上一生活日短期修正之和，morningAdjustment 为 0。
- 跳过状态显示估计值及“未进行晨间确认”，不显示占位符。
- 补做后 appliedDelta 正确重放。
- 补做后初始估计、当前估计、档位和能量球状态同步更新。
- dailyAbsolute 唯一。
- 先选择实际、后显示差异。
- 次日补充不更新摘要。
- 相对校正不改变 currentEstimate。

## 10.5 验收标准

- 页面文案始终区分“估计”和“实际”。
- 原始观测完整保存。
- MVP-A 没有任何自动参数更新路径。
- 每日确认可跳过且不阻断记录。
- 跳过、首次完成、补做完成和再次编辑四种晨间状态均有唯一且可测试的界面表现。

# 11. 阶段 7：首页、概览与提醒

## 11.1 目标

## 11.2 开发步骤

- 总时长
- netDelta
- 按 grossDelta 排序

6. 展示当天记录入口和记录列表入口。
7. 实现中低、低和估计透支提醒。

- 点击式入口满足合理触控区域。
- 字体放大时核心数字不截断。
- 低饱和提示仍需满足对比度。

- 四大类概览排序。
- 同档提醒只出现一次。

- 点击记录入口稳定。

- 主要布局在 Pixel_7 模拟器无溢出。
- HTML 参考原型中的首页、概览、提醒、撤销和揭示五个场景均有对应 Flutter 实现；差异已记录且有明确原因。

# 12. 阶段 8：结算、昨日与滚动总结

## 12.1 目标

- 不出现任何自动调整按钮。

## 12.5 验收标准

- 估计和实际两列来源清楚。

# 16. 阶段 12：七日自用验证

## 16.1 目标

验证产品是否值得继续，而不只是验证代码能运行。

## 16.2 每日记录

每天自动或手动记录：

- 是否主动打开
- 活动记录条数
- 是否完成每日实际状态
- 补记 / 编辑 / 删除次数
- 无法分类次数
- 随时校正方向
- 崩溃和数据异常
- 当天主观记录负担
- 估计是否有参考价值

## 16.3 通过标准

- 7 个自然日中至少 5 天主动使用。
- 至少 4 次每日实际状态确认。
- 活动补记、编辑、删除、重算和结算无数据错误。
- 估计精力对当天判断具有实际参考价值。
- 不频繁出现无法归类或必须绕路。
- 点击式入口稳定可用。
- 手势只有达到 18/20 且零误记才成为默认入口。

## 16.4 失败时处理

- 记录负担高：优先减少步骤，不增加自动学习掩盖问题。
- 分类缺口多：先分析四个“其他”的使用，再决定调整固定子类。
- 估计无参考价值：检查规则和双轨反馈，不进入 MVP-B。
- 实际状态完成率低：调整提示时机和文案。
- 数据错误：停止验证，修复并重新开始完整 7 天。

## 16.5 MVP-B 门槛

7 日验证通过也不立即启用自动建议。

继续积累到至少 14 个带每日实际状态的有效日后，才允许：

- 评估基准线建议算法
- 根据具体活动直接反馈研究 personalFactor 阈值

在真实数据足够前，不提前写死 personalFactor 样本数、步长或范围。
