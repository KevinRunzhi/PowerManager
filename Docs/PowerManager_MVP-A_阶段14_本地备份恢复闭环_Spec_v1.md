- 版本：1.0

# 1. 背景与问题

应用已能导出包含七类 MVP-A 数据的 JSON，但目前只能“导出并分享”，无法在应用内验证、
预览和恢复。导出文件因此只能用于人工审计，尚未形成真正的备份恢复闭环。

恢复属于高风险数据操作。当前数据库还有以下约束：

1. `daily_summaries` 禁止更新和删除；
2. `app_settings` 单例行禁止删除；
3. 已被引用的规则版本禁止更新；
4. 活动和日总结通过规则版本外键关联；
5. 每个生活日最多存在一个 `dailyAbsolute` 观测；
6. 提醒回执具有 `(type, scopeKey, action)` 唯一性。

因此不能逐条覆盖，也不能在现有数据上直接合并。阶段 14 采用：

> 严格检查备份包，展示替换影响，自动保存当前数据的安全副本，再以单个数据库事务完整替换。

---

# 2. 目标与非目标

## 2.1 目标

1. 从系统文件选择器选择单个 `.json` 文件；
2. 在不写数据库的情况下完成完整解析与校验；
3. 展示来源、导出时间、数据数量、生活日范围和替换说明；
4. 用户二次确认后才允许恢复；
5. 恢复前自动生成当前数据安全副本；
6. 七组数据和设置必须在一个事务内完整替换；
7. 任一步失败时，当前数据库保持原样；
8. 恢复成功后刷新全部派生状态，并可分享恢复前安全副本。

## 2.2 非目标

- 不合并两个备份；
- 不处理 `schemaVersion != 1` 的迁移；
- 不导入未知第三方格式；
- 不修改备份中的历史值或自动修复损坏数据；
- 不恢复 APK、偏好设置、缓存或系统权限；
- 不把备份上传到服务器；
- 不加入自动学习或跨设备同步。

---

# 3. 核心决策

## 3.1 恢复语义：完整替换

恢复成功后，数据库中七组业务数据与备份完全一致。当前数据库中不存在于备份的记录也会
被移除。禁止使用“按主键跳过”“较新记录优先”等隐式合并策略。

原因：日总结不可变、活动存在逻辑删除、规则版本参与稳定重放；合并会产生难以解释的冲突。

## 3.2 支持策略：仅精确支持 schema v1

- `schemaVersion == 1`：继续检查；
- 小于 1、缺失、非整数：拒绝；
- 大于 1：拒绝，并提示当前应用版本不支持；
- 不根据 `appVersion` 阻止恢复，`appVersion` 只用于来源展示。

## 3.3 文件上限与隐私

- 文件扩展名必须为 `.json`；
- 最大 10 MiB，超出后在读取/解析前拒绝；
- 使用严格 UTF-8 解码；
- 文件内容只在本机处理；
- 错误界面不得展示活动名称、ID 或原始 JSON 片段；
- 日志不得输出备份正文。

## 3.4 恢复前安全副本

在正式写入前，应用使用当前导出服务生成安全副本，并保存为应用支持目录中的固定文件：

`powermanager-before-last-restore.json`

写入采用临时文件加重命名，避免留下半份安全副本。恢复成功后，设置页显示
“分享上次恢复前备份”。后续恢复会覆盖上一份安全副本。

如果安全副本写入失败，则不得开始恢复。

# 4. 用户流程

## 4.1 入口

设置 → 数据：

1. `导出并分享 JSON`；
2. `从 JSON 备份恢复`；
3. 存在安全副本时显示 `分享上次恢复前备份`。

恢复按钮在处理期间禁用，文案变为“正在检查…”或“正在恢复…”。导出和恢复不可并发。

## 4.2 选择与检查

1. 打开 Android 系统文件选择器；
2. 限制单选和 JSON 扩展名；
3. 用户取消时安静返回，不显示失败提示；
4. 选中文件后读取字节并严格检查；
5. 检查失败只展示安全、可行动的中文错误。

错误分为：

- 文件过大；
- 不是有效 UTF-8 / JSON；
- 缺少字段或字段类型错误；
- 备份版本不支持；
- 数据违反唯一性、引用关系或业务规则；
- 文件读取失败。

## 4.3 预览

检查通过后打开底部 Sheet，展示：

- 文件名；
- 来源应用版本；
- 导出时间（本地时间）；
- 最早至最晚生活日；
- 七组数据计数；
- 当前数据与备份数据的总量对比；
- 明确警告：恢复会完整替换当前数据；
- 说明：开始前会自动保存当前数据副本。

预览阶段不得写数据库或创建安全副本。

## 4.4 二次确认

点击“继续恢复”后显示确认 Dialog：

- 标题：`确认替换当前数据？`
- 正文：`备份通过检查。恢复会替换当前全部记录，过程中请不要关闭应用。`
- 取消：`暂不恢复`
- 确认：`保存副本并恢复`

只有确认按钮可以触发写操作。

## 4.5 结果

成功：

- 关闭预览；
- 刷新当前投影、晨间状态、实际状态、历史回顾和设置；
- 显示 `恢复成功，已保存恢复前安全副本。`；
- 返回首页并重新准备当前生活日。

失败：

- 保持在设置页；
- 显示 `恢复失败，当前数据未改变。`；
- 不展示内部异常；
- 允许重新选择文件。

# 5. 校验规则

校验必须在任何数据库写入之前完成，并返回不可变的类型化备份对象。

## 5.1 顶层结构

必须包含：

- `schemaVersion`
- `exportedAt`
- `appVersion`
- `appSettings`
- `ruleConfigVersions`
- `morningCheckIns`
- `activityRecords`
- `energyObservations`
- `dailySummaries`
- `promptReceipts`

日期时间必须是带时区的 ISO-8601，并转换为 UTC。`lifeDay` 必须是合法的 `yyyy-MM-dd`。

## 5.2 设置与规则

- 基准线和待生效基准线范围为 60～140；
- 待生效值和生效生活日必须同时为空或同时存在；
- 活跃规则版本必须存在；
- 待生效规则版本存在时，也必须能在规则列表找到；
- 规则版本非空且唯一；
- 规则 `values` 必须为 JSON 对象。

## 5.3 晨间确认

- `id` 唯一且非空；
- `lifeDay` 唯一；
- 四个枚举值必须受支持；
- `morningAdjustment` 必须等于总体状态规则值；
- MVP-A 持久化数据不得使用 `skipped` 总体状态。

## 5.4 活动

- `id` 唯一且非空；
- 大类必须与子类所属大类一致；
- 时长只允许 15/30/45/60/90/120；
- 引用的规则版本必须存在；
- `theoreticalDelta` 必须与对应规则版本、子类和时长一致；
- `active` 必须没有 `deletedAt`；`deleted` 必须存在 `deletedAt`；
- `createdAt <= updatedAt`；
- 同一生活日内按稳定重放顺序重新计算时，`appliedDelta` 必须一致。

## 5.5 实际状态与校正

- `id` 唯一且非空；
- 每个生活日最多一个 `dailyAbsolute`；
- `dailyAbsolute` 只能有 `absoluteState`；
- `relativeCorrection` 只能有 `relativeState`，且必须包含观测时估计值。

## 5.6 日总结

- `lifeDay` 唯一；
- 基准线 60～140；
- 晨间调整只允许 -6/0/6；
- 短期调整只允许 -4～0；
- 消耗和恢复不得为负；
- 标准有效日与弱有效日不得同时为真；
- 引用规则版本必须存在；
- 分类汇总的大类、时长、净变化和绝对变化必须合法；
- 日总结必须与该生活日的晨间确认、活动稳定重放结果一致。

## 5.7 提醒回执

- `id` 唯一且非空；
- 枚举值必须受支持；
- `scopeKey` 非空；
- `(type, scopeKey, action)` 唯一。

# 6. 原子恢复设计

## 6.1 写入顺序

在单个 Drift/SQLite 事务内：

1. 临时移除只用于阻止正常业务删除/更新的触发器；
2. 按外键安全顺序清空七张业务表；
3. 先写规则版本，再写设置；
4. 写晨间确认、活动、观测、日总结、提醒回执；
5. 恢复保护触发器；
6. 执行 `PRAGMA foreign_key_check`；
7. 核对七组记录计数；
8. 提交事务。

触发器只在该事务连接中、该事务生命周期内移除。任何异常必须使触发器和旧数据一起回滚。

## 6.2 失败注入

数据库测试必须能在清空后、部分插入后注入异常，证明：

- 旧数据仍完整存在；
- 新数据没有残留；
- 保护触发器仍有效。

# 8. 验收标准

1. 取消文件选择不报错、不改变数据；
2. 非 JSON、损坏 JSON、超限文件均被拒绝；
3. 不支持的 schema 版本被拒绝；
4. 七组数据任一字段或业务关系损坏时被拒绝；
5. 校验失败时数据库零写入；
6. 预览准确展示文件元信息、生活日范围和七组计数；
7. 未进行二次确认时数据库零写入；
8. 安全副本失败时不得开始恢复；
9. 恢复成功后重新导出的七组数据与选中备份一致；
10. 恢复中途异常时旧数据完整保留；
11. 恢复后数据库外键和保护触发器仍有效；
12. 设置页可分享最近一次恢复前安全副本；
13. 200% 字号与小屏下无溢出；
14. `dart format`、`flutter analyze`、完整 `flutter test` 通过；
15. Pixel_7 模拟器完成选择、预览、取消、确认和成功反馈；
16. 真机综合验收继续延期到 MVP-B 完成后。
