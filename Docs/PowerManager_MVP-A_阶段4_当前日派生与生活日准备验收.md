# 1. 本阶段完成内容

本阶段打通以下三条核心链路：

1. `CurrentDayProjectionService`
   - 从持久化数据读取当日晨间确认；
   - 只读取“严格相邻的上一生活日”结算，计算短期修正；
   - 读取当日有效活动并按 `completedAt → createdAt → id` 重放；
   - 返回基础值、规则版本、晨间修正、短期修正、初始估计、当前估计、档位、活动顺序和分类汇总。
2. `SettlementService`
   - 从晨间确认、有效活动和实际状态观测中收集待结算生活日；
   - 只处理当前生活日之前且尚未结算的非空生活日；
   - 按生活日从旧到新结算；
   - 空白生活日不创建摘要；
   - 已有摘要保持不可变。
3. `OperationPreparationService`
   - 支持冷启动、恢复前台、写操作前三类触发；
   - 在同一事务中依次执行“结算旧日 → 应用到期设置 → 派生当前日”；
   - 重复调用保持幂等；
   - 应用启动及恢复前台已接入准备服务；
   - 后续阶段的所有写用例必须在写入前调用 `prepare(beforeWrite)`。

# 2. 方案修正：待启用规则补充生效生活日

阶段 4 实现前复核发现：

- 技术方案要求 `pendingRuleVersion` 从下一生活日起生效；
- 原 `app_settings` 只有待启用规则版本，没有记录其目标生活日；
- 仅凭“是否存在 pending”无法可靠区分未到期、已到期和跨多日未启动三种状态。

本阶段补充：

```text
pendingRuleEffectiveLifeDay
```

数据库同时增加成对约束：

```text
pendingRuleVersion 与 pendingRuleEffectiveLifeDay
必须同时为空，或同时存在
```

基础估计值继续使用同样的成对字段策略。由于应用尚未进入可持有用户数据的发布阶段，且生产 UI 在本阶段前未打开数据库，本次属于首次发布前的 Schema v1 完整性修正，不增加迁移版本；阶段 3 的 Git 提交仍可作为修改前快照。

# 3. 固定执行顺序

每次准备严格执行：

```text
读取当前时间
  → 计算 04:00 边界下的 currentLifeDay
  → 开启 Drift 事务
  → 使用旧的 active 设置结算过去非空生活日
  → 应用已到期 pendingBaseEnergy
  → 应用已到期 pendingRuleVersion
  → 清空已经应用的 pending 值及其生效日
  → 使用新 active 设置派生当前日
  → 提交事务并返回可解释结果
```

这样可以保证：

- 旧生活日不会误用刚生效的新基础值或规则；
- 当前生活日不会继续使用已经到期的旧设置；
- 中途失败不会留下半批摘要或只更新一半设置；
- 在前台停留跨过 04:00 后，第一笔写入仍会先完成换日准备。

# 4. 非空日与迟到观测规则

生活日只要存在以下任一来源，即视为非空：

- 一条晨间确认；
- 一条有效活动；
- 一条实际状态或相对校正观测。

逻辑删除的活动不使生活日变为非空。完全没有上述来源的日期不生成 `daily_summary`。

如果某生活日已结算，之后才补写该日实际状态：

- 观测事件照常保存；
- 已有摘要不更新、不删除、不重算；
- 后续准备通过主键、幂等插入和不可变触发器共同保证摘要稳定。
